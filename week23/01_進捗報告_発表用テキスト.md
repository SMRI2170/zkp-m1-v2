# Week 23 進捗報告 — 発表用テキスト

基準日: 2026-10-04  <br>
用途: 研究進捗報告。スライドへ転記できる要点と、口頭説明の補助をまとめる。

## 最初に伝える結論

複数観測者の入力からleaf proofを作り、集約前に検証する部品は実装・部分検証が進んだ。  <br>
再帰proofを一本につなぎ、最終proofをEVMで検証する段階と、実機の複数観測データによる評価はこれからである。

## スライド1 — 研究目的と現在地

### スライド本文

- 複数の観測端末が、Remote IDの位置と受信RSSIの整合性を個別に確認する。
- 端末の正確な位置や生RSSIを公開せず、観測結果を集約する。
- 最終目標は、集約結果をゼロ知識証明で検証し、EVMへ記録すること。
- 現在地: leaf proofと集約前の検証を部分実証。proof一本化と実データ評価は未完了。

### 口頭説明

「放送される位置だけでは、その位置に機体がいるか分かりません。複数の端末が受けた電波強度と放送位置の整合性を確認し、端末の生データを公開せずに結果を集約するのが目的です。現在は部品ごとの検証が進みましたが、最終proofをEVMまで通す全経路はまだ完成していません。」

## スライド2 — 検証の流れ

### スライド本文

```text
BLE Remote ID / RSSIを受信
          ↓
各観測端末がleaf proofを作成
          ↓
Bridgeがleaf proofと登録membershipを検証
          ↓
再帰ノードが観測を集約し、重複を防止
          ↓
最終proofをEVMで検証・記録
```

- leaf proof: 1件の観測が回路内の条件を満たすことを示す証明。
- nullifier: 同じ端末を同じsessionで二重に数えないための識別状態。
- 各段階の接続状態を分けて報告する。

### 口頭説明

「leaf proofは観測1件の証明です。Bridgeはその証明と端末membershipを確認します。再帰ノードは複数の証明を安全にまとめ、nullifierで同じ端末の再利用を防ぎます。いまは各部品の検証結果があり、最後までつながった一つのproofはまだありません。」

## スライド3 — 現在の実装状況

### スライド本文

| 段階 | 状態 | どこまで確認したか |
|---|---|---|
| Captureからwitness作成 | 合成入力で確認 | capture-to-witness処理を合成JSONLで検証。実地captureデータは未取得。 |
| V2 leaf proofとbatch | proof testで確認 | test用鍵のfresh leaf proof、batch受理、public signal改ざん拒否を確認。 |
| BridgeBWV2 | 回路関係を部分確認 | test engineでsolveし、member/profile pathの改ざんを拒否。outer proof生成ではない。 |
| 再帰集約・FinalBN | 部品を実装 | Node、nullifier併合、state encoding、FinalBNなどの部品あり。全段の実proof接続は未完了。 |
| EVM最終検証 | 未完了 | 実際の再帰root proofを最終verifier / registryで検証していない。 |

### 口頭説明

「表の『確認済み』は、その行に書いた範囲までです。特にBridgeは回路の制約をtest engineで解いたところまでで、BridgeのGroth16 proofを作って再帰チェーンへ流した状態ではありません。」

## スライド4 — 今回確認したこと

### スライド本文

- RSSI-only V2 leafを更新し、距離不整合の観測も集約対象として扱えるようにした。
- test用leaf proof 3件の例で、正常1件・不整合2件から `consistent=1 / suspicious=2` を導出。
- その例を `pcd3 --stage=plan` で読み、3つの異なる鍵、profile set `{1,2}`、疑いあり verdictを確認。
- BridgeBWV2のtest-engine solveでfar-mismatch leafを処理し、誤ったmember/profile pathを拒否。
- local Solidity leaf verifierが正常proofを受理し、RID commitment、time bucket、consistency、freshness、profileの改ざんを拒否。

### 口頭説明

「ここで示しているのは、合成fixtureとtest用setup鍵を使った回路・proofの検証です。正常と不整合を件数へ正しく分け、いくつかの改ざんを拒否できました。実際の観測者や実地データで再現した結果ではありません。」

## スライド5 — 証明の意味と評価上の限界

### スライド本文

**現時点で示したこと**

- 定めた回路条件の下で、leaf proofやbatchの入力を検証できる。
- 登録rootを入力したBridge制約でmembershipを確認する部品がある。

**これから確認すること**

- Remote IDの署名・endorsement chainをtrust rootまで検証すること。
- 実端末のcredential登録、独立した位置真値を用いたRSSI評価。
- Bridgeから最終proof、EVM記録までの連続した実proof。

**現在の説明範囲:** Remote IDの機体認証ではなく、claimed RIDに対する位置不整合の評価。認証状態は `not_evaluated`。

### 口頭説明

「proofは、入力データが回路で定めた関係を満たすことを示します。現状のRemote ID認証処理は未評価なので、『登録機の真正性を確認した』とは説明しません。いまの判定はclaimed RIDに対する位置不整合の評価です。また、実captureと独立真値の評価がないため、現場での検出精度もまだ主張できません。」

## スライド6 — Nova PoCと再帰PCDの位置づけ

### スライド本文

- Nova PoC: RSSI判定と件数更新を3 stepで逐次実行し、Android実機でproof生成・検証を確認。
- Nova PoCには、現行leaf proof、membership、nullifier、EVM Deciderが未接続。
- Week 23ではBridgeBW、曲線間state、nullifier併合、FinalBNなど再帰PCD側の部品を実装・検証。
- Novaの逐次更新PoCと、再帰PCDの現在の実装部品は、別の検証経路として扱う。

### 口頭説明

「Novaの結果は、同じ更新を繰り返すPoCとして有効です。一方で、Nova PoCがleafからEVMまでの現行経路に接続されたわけではありません。Week 23で進めている再帰PCDの部品も、全体の再帰proofとしてつながった段階ではありません。」

## スライド7 — 次の完了条件

### スライド本文

1. 現行leaf proofからBridge自身のGroth16 proofを作り、固定VK・active member rootと一緒に検証する。
2. Bridge → recursive Node → FinalBNを実proofで接続し、重複端末・異なるsession・改ざん入力を拒否する。
3. 最終proofをEVM verifier / registryで受理させ、proof size・時間・gasを測る。
4. 複数の実観測者によるcaptureと独立した位置真値で、校正・holdout評価を行う。

### 口頭説明

「次の節目は、部品の存在ではなく、拒否条件を含む実proofを一本の経路で通すことです。並行して実データを集め、校正用データと評価用データを分けてRSSIの誤検知・見逃しを報告します。」

## 発表時の短い説明

「研究の目標は、複数端末のBLE Remote ID / RSSI観測から位置不整合を検証し、端末の正確な位置や生RSSIを公開せずに集約することです。Week 23では、V2 leaf proof、batch、Bridgeの回路制約、曲線間stateやnullifier併合などの部品を実装・部分検証しました。合成fixtureでは、正常1件と不整合2件の集約、およびいくつかの改ざん拒否を確認しています。一方、実地capture、Remote ID trust chain、BridgeからEVMまでの実proof一本化は未完了です。次は再帰経路を実proofで接続し、複数観測者の実データで性能と誤検知を評価します。」

## 発表で使う用語の説明

- **witness:** proofを作るときに使う観測入力。現在の実験では合成データを含む。
- **leaf proof:** 1件の観測について、公開せずに回路条件を満たすと示すproof。
- **Bridge:** leaf proofを検証し、その結果を再帰集約へ渡す回路。
- **membership:** 端末の公開鍵が、指定された登録端末一覧に含まれること。
- **nullifier:** 同じ端末を同じsessionで一度だけ数えるための値。
- **test-engine solve:** 回路の制約を満たす入力か確かめる検査。Groth16 proofの生成やEVM検証を意味しない。
- **synthetic fixture:** 実機から取った記録ではなく、テスト用に作った入力一式。
- **EVM:** Ethereum互換コントラクトを実行する環境。この研究では最終proofの検証先。

## 想定質問と短い回答

**Q. ドローンのRemote IDは認証済みですか？**  <br>
A. いいえ。現状の認証状態は `not_evaluated` です。位置不整合はclaimed RIDに対する結果として扱います。

**Q. 実機で動作しましたか？**  <br>
A. Novaの3-step PoCはPixel 8で実行済みです。現在のcapture-to-V2 proof経路と再帰PCD全体は、実地BLE captureからEVMまでの実機E2Eとしては未検証です。

**Q. もうEVMに記録できますか？**  <br>
A. registryやverifierの部品はありますが、現在の再帰経路から生成した最終proofを使うEVM E2Eは未完了です。

**Q. 何を証明しているのですか？**  <br>
A. leaf proofは、非公開入力が回路内のRSSI・時間などの条件を満たすことを示します。現状のprofileでは、機体の登録上の真正性やセンサーの物理的な正しさまでは証明しません。

**Q. Novaを採用したのですか？**  <br>
A. Novaの逐次更新PoCは確認済みですが、現行leaf・membership・nullifier・EVMまでつないだ比較評価は未完了です。Nova PoCを本番経路の完成とは扱いません。

## 補足: Nova PoCの計測値

Nova調査スライドを補足資料として使う場合の値。各環境の条件は異なるため、AndroidとM2 Macの時間を直接比較しない。

| 環境 | 3 stepのproof生成 | 最終verify |
|---|---:|---:|
| Pixel 8 | 485 / 655 / 1,198 ms | 172 ms |
| M2 Mac | 135 / 151 / 281 ms | 28 ms |

この計測が示すのは3-step逐次更新PoCの動作であり、leaf真正性、重複防止、10-step性能、EVM検証の実証ではない。
