# ノード間で前の証明を次の証明へ接続するときの保証範囲

## 結論

ノードAが作ったproofをノードBが受け取り、Bが次のproofを作るとき、守る対象は4つに分かれる。

| 層 | 問い | 主な仕組み |
| --- | --- | --- |
| 観測 | この値は現実に観測されたか | 端末保護、署名済み取得経路、校正、独立観測者 |
| 計算 | 与えられた入力から正しくstateを更新したか | leaf proof、Bridge、再帰proof / Nova |
| 通信 | ノード間でpacketが変更されていないか | canonical encoding、hash、電子署名 |
| 履歴 | ノードAが異なる履歴を複数ノードへ配っていないか | quorum certificate、threshold signature、確定root |

**ZKPは計算の正しさ、署名はpacketの出所と完全性、quorum / consensusは共有履歴の一意性を扱う。**

---

## 1. ノードAからBへ渡すもの

再帰proofの親ノードは、子proofと子stateを回路内で検証する。概念上の受渡しは次である。

```text
Node A
  proof_A
  state_A = (
    protocolVersion,
    droneIdCommitment,
    timeBucket,
    policyCommitment,
    memberRoot,
    oldNullifierRoot,
    newNullifierRoot,
    consistentCount,
    suspiciousCount
  )
       |
       v
Node B
  proof_Aがstate_Aを証明することを回路内で検証
  自分が追加する有効leaf / 子proofと結合
       |
       v
  proof_AB, state_AB
```

位置、RSSI、端末秘密鍵、Merkle path、nullifier leafなどは、親回路のprivate witnessであり、最終stateには出さない。

---

## 2. 通信途中でstateを書き換えた場合

例として、Aが次を送る。

```text
state_A = (timeBucket=100001, consistentCount=2, suspiciousCount=1)
proof_A = pi
signature_A = sigma
```

署名はpacket全体の正規化済み表現に対して作る。

```text
sigma = Sign_A(
  H(protocolVersion || vkHash || proof_A || canonical(state_A))
)
```

第三者が `consistentCount=2` を `100` に変えると、受信したpacketのhashはAが署名したhashと異なる。Bは署名検証に失敗し、packetを拒否する。

さらに、stateがproofのpublic inputとして束縛されているなら、次も成り立つ。

```text
Verify(vk, pi, state_A)  = 1
Verify(vk, pi, altered_state_A) = 0
```

したがって、第三者によるstate変更は次の二重の検査で検出する。

1. **署名検証**: Aがそのpacketを送ったか、通信中に変化していないか。
2. **proof検証**: `proof_A` が受信stateを本当に証明しているか。

proofとstateを別々に扱い、stateをproofのpublic inputに入れない設計では、proof検証だけでstate改竄を防げない。stateは必ずpublic inputとして束縛する。

## 3. 「Aが嘘をつく」を分けて扱う

### ケースA: Aが計算結果を勝手に書き換える

本来は `consistentCount=2` となる入力・前stateから、`consistentCount=100` とするproofを作ろうとする場合である。

```text
正しい入力と前state
      |
      v
回路の状態遷移
      |
      +-- (2, 1)   -> proofを作れる
      |
      +-- (100, 1) -> 制約を満たせずproofを作れない
```

これはZK proof / 再帰proofが防ぐ範囲である。親回路は子proofのcount、nullifier root、同一session条件を再検証し、新stateを回路内で計算する。

### ケースB: Aが入力そのものについて嘘をつく

実際は `RSSI=-80` だったのに、Aが最初から `RSSI=-60` を入力してleaf proofを作る場合である。

```text
偽の観測入力
      |
      v
回路はその入力に対して正しく計算
      |
      v
有効なproofを作れる可能性がある
```

ZKPが示すのは「与えられた入力に対して計算が正しい」ことであり、入力が現実の観測値そのものであることではない。この問題には、署名済み取得経路、端末鍵の保護、校正、複数独立観測者、端末attestationが必要である。

---

## 4. 二重計上・別session混入・proof差替え

親回路に次の制約を入れることで、前proofから次proofへの接続で発生する改竄を拒否する。

| 攻撃 | 回路上の検査 | 結果 |
| --- | --- | --- |
| 壊れたproofへの差替え | 固定verification keyで子proofを回路内検証 | 拒否 |
| proofと別stateの組合せ | 子proofをそのstateのpublic inputで検証 | 拒否 |
| 別ドローンの混入 | `droneIdCommitment` の一致 | 拒否 |
| 別時間枠の混入 | `timeBucket` の一致 | 拒否 |
| 別policyの混入 | `policyCommitment` の一致 | 拒否 |
| 未登録端末の参加 | `memberRoot` に対するmembership検証 | 拒否 |
| 同一端末を二度数える | nullifier集合の重複検出とroot更新 | 拒否 |
| 別回路 / 別versionのproof | protocol versionと固定VKのpinning | 拒否 |
| 曲線間stateの解釈差 | BN254値を64 bit x 4 limbで正規化 | 拒否 |

---

## 5. receiptだけではforkを防げない

単純に複数ノードのreceiptを集めるだけでは、Aが二つの異なるpacketを別々のノード集合に送ることを止められない。

```text
          Node A
          /    \\
        H1      H2
       /          \\
    B,C,D        E,F,G
```

このため、同じ `sessionId` と `height` について、ノードが一つのhashにしか投票しない規則が要る。さらに、二つのquorumが必ず少なくとも一つのhonest nodeで重なる大きさを選ぶ。

Byzantine nodeが最大 `f` 台で、全体が `3f+1` 台なら、通常は `2f+1` 署名をquorum certificateとする。

```text
同じ (sessionId, height) について
  - 各ノードは一つの packetHash にだけ署名する
  - 2f+1 個の署名がそろったhashだけを確定する
  - 次のproofは、その確定hash / quorum certificateを束縛する
```

この仕組みで、異なる履歴を同時に確定することを防ぐ。閾値署名を使えば、`2f+1` 個の個別署名を一つのcertificateにまとめられる。

---

## 6. なお残る限界

| 問題 | 再帰proofだけでの対処 | 必要な追加策 |
| --- | --- | --- |
| Aが受信したproofを捨てる | 不可 | 提出期限、受領ログ、可用性監査 |
| Aが送信前に偽入力を作る | 不可 | 端末attestation、独立観測、校正 |
| Aの鍵が漏洩する | 不可 | secure element、鍵失効、再登録 |
| ネットワーク妨害 | 不可 | relay冗長化、queue、再送 |
| 全quorumが共謀する | 不可 | 独立運営、外部アンカー、信頼境界の見直し |

---

## 発表用の短い説明

> 前のproofを次のノードへ渡すとき、ZK proofは状態遷移の正しさを確認します。署名は受け渡すpacketが途中で変わっていないことを確認します。複数ノードが一つのhashにだけ署名するquorum certificateにより、異なる履歴を同時に確定できないようにします。センサが最初から虚偽値を出す問題は別の層で扱います。
