# フレームワーク比較 — 何ができる / メリット / デメリット

作成日: 2026-07-17 / 目的: 各 ZKP フレームワークが「何ができるか」を、メリット・デメリットで
わかりやすく並べる。手法の全体像は [01_手法の全体像.md](01_手法の全体像.md) を先に参照。
※ 状況は 2026年前半時点。採用前に最新版で再確認すること。

前提知識（1行）: フレームワークは「証明系エンジン(層2)＋回路を書く言語」の組み合わせ。
本案件の回路要件 = **Poseidonハッシュ / EdDSA署名検証(Baby JubJub) / 比較・範囲 / ~18k制約 /
オンチェーン検証 / 多端末集約**。

## 1. circom + snarkjs / rapidsnark（現行）
- **できること**: circom で回路記述 → snarkjs(JS) / rapidsnark(C++) で Groth16 証明。circomlib に
  Poseidon・EdDSA・比較が揃い、本案件の回路はこれで実装済み。rapidsnark は端末で高速。
- **メリット**:
  - 証明が最小・オンチェーン検証が最安（≈348k gas）
  - ライブラリと実績が豊富、既に動いている
  - rapidsnark で arm64 実機証明が実用的
- **デメリット**:
  - **回路ごとにトラステッドセットアップの儀式が必要**（★1脆弱性の温床）
  - 回路更新のたびに儀式のやり直し
  - 低レベルで、複雑な回路は書きにくい
- **本案件**: 現状維持の基準。端末証明の土台として妥当。

## 2. gnark（現行の集約器）
- **できること**: Go で回路記述、Groth16/PLONK。再帰検証で「N個の証明を検証する証明」を作れる（M2）。
- **メリット**:
  - プローバが高速、Go で書けて実装しやすい
  - 再帰・Merkle・MiMC などライブラリが揃い、集約に向く
  - EVM 向け verifier を出力できる
- **デメリット**:
  - サーバ向き。**端末での証明生成は重く非現実的**
  - Groth16 なら回路別セットアップが必要
- **本案件**: **集約(M2)はこれで継続**が妥当。端末証明器の候補ではない。

## 3. Noir + Barretenberg
- **できること**: 高水準言語 Noir で回路記述、バックエンド bb(UltraHonk) で証明。
  Poseidon 標準、EdDSA(Baby JubJub) 実装あり(約24k制約)、比較も可 → 本案件の回路を**移植すれば実現可能**。
- **メリット**:
  - **回路別セットアップ不要（1回の準備を使い回し）→ ★1を根治**
  - 言語が書きやすく、クライアント証明が速い（比較でGroth16系の5〜50倍の例）
  - Mopro 経由で iOS/Android/**Flutter** に載る
- **デメリット**:
  - **オンチェーン検証が約2.4M gas（Groth16の約7倍）**＝コスト増
  - circom→Noir の回路移植が必要
  - 集約系を現行 gnark から組み替える必要
- **本案件**: 「セットアップ根治＋端末で速く」の第一候補。ただしオンチェーンコストと集約再設計がトレードオフ。

## 4. halo2
- **できること**: Rust で chip/gadget を組んで回路化。PLONK(KZG=準備1回 / IPA=準備不要)。
  Poseidon gadget あり。ECC gadget はあるが EdDSA は自作寄り。
- **メリット**:
  - lookup / custom gate など**高度で効率的な回路**が書ける
  - 回路別セットアップ不要
  - Mopro でモバイル対応
- **デメリット**:
  - **学習コストが高く実装が難しい**（新規者に厳しい）
  - Baby JubJub の EdDSA 実装は手間大
  - Groth16 ほど検証は安くない
- **本案件**: 特殊機能が要らなければ**費用対効果が悪い**。積極採用しない。

## 5. Plonky2 / Plonky3
- **できること**: Rust で回路記述、STARK(FRI)。Poseidon は Goldilocks 体でネイティブ高速。再帰が速い。
- **メリット**:
  - **トラステッドセットアップ不要**
  - **再帰が非常に速く、集約を軽くできる**
  - 証明生成が速い
- **デメリット**:
  - 使う体が Goldilocks で、**現行の EdDSA(BN254系 Baby JubJub) と不一致→非ネイティブ演算で高コスト**
  - 証明が大きく、EVM 検証は圧縮(wrap)が必要で高価
  - 低レベルで記述が重い
- **本案件**: 署名検証を含む端末回路には不向き。**集約用途**としては魅力。

## 6. Nova / HyperNova / Sonobe（Folding）
- **できること**: Rust。計算を「1ステップの回路」に書き、N 個を逐次“畳み込んで(fold)”最後に1証明へ圧縮。
  arkworks ベースで BN254/Baby JubJub を扱える。
- **メリット**:
  - **省メモリで、端末やコーディネータ端末で集約できる**
  - Folding 自体は回路別セットアップ不要
  - 「N端末を1つに」という本案件の集約にそのまま合う
- **デメリット**:
  - ステップ回路への**再設計が必要**、比較的新しく事例が少ない
  - 最終圧縮の証明系（Groth16等）でセットアップが要る場合あり
  - オンチェーン検証コストは最終圧縮方式に依存
- **本案件**: **集約(M2)の代替**として最有力の研究的選択肢。端末側集約を狙うならこれ。

## 7. RISC Zero / SP1（zkVM）
- **できること**: **普通の Rust コード**を書くと、その実行の正しさを STARK で証明。回路を意識しない。
- **メリット**:
  - 回路設計が要らず、複雑なロジックを普通のコードで書ける
  - セットアップ不要、汎用性が非常に高い
- **デメリット**:
  - **端末での証明生成が重い**（今はサーバ/GPU前提）
  - 証明が大きく、EVM 検証は圧縮が必要
- **本案件**: 将来枠。今のモバイル端末証明には重い。

## 8. Cairo / Stwo（Starknet）
- **できること**: Cairo 言語で記述、STARK。Poseidon ネイティブ。モバイル実機での大規模実証あり（5秒以内）。
- **メリット**:
  - **セットアップ不要・モバイル証明の実績が豊富**
  - Poseidon が速い
- **デメリット**:
  - 署名は Stark 曲線が native で、**Baby JubJub は自作寄り**
  - **検証が Starknet 前提**＝現行 EVM＋gnark とエコシステムがずれる
- **本案件**: 決済/集約レイヤを Starknet に替える話になり、EVM 前提と不整合。今回は見送り寄り。

## 9. Mopro（モバイル配布ツールキット）
- **できること**: 証明系そのものではなく、**上記(circom+Groth16 / halo2 / Noir 等)をモバイルアプリの
  バインディングに変換する橋渡し**。iOS(Swift)/Android(Kotlin)/**Flutter**/React Native。
- **メリット**:
  - **現行 circom 回路をそのまま**モバイルで動かせる＝移行コスト最小
  - Flutter パッケージがあり、今のアプリと直結
  - 後から halo2/Noir へ差し替えても同じツールで対応
- **デメリット**:
  - 証明系の性質（セットアップ・gas）は中で選んだものに従う（Mopro自体は解決しない）
  - iOS シミュレータ非対応、Android は arm64 実機/エミュ必須
- **本案件**: **端末証明を今すぐ堅くする最短路**。手法・エンジンを変えずにモバイルを固められる。

## 目的別のおすすめ（結論）

| やりたいこと | 手法(層) | フレームワーク |
|---|---|---|
| 今のまま端末証明を堅く・モバイル最適化 | 現行維持 | **Mopro（circom+rapidsnark, Flutter）** |
| ★1トラステッドセットアップを根治したい | 層2をPLONK系へ | **Noir + Barretenberg**（gas増と集約再設計は覚悟） |
| 多端末集約を端末側・省メモリでやりたい | 手法4 Folding | **Nova / Sonobe** |
| 集約の再帰を速く・準備不要にしたい | 手法3 再帰 | **Plonky2**（or 現行 gnark 継続） |
| 複雑ロジックを普通のコードで（将来） | zkVM | RISC Zero / SP1 |

**総合の現実解**: 端末は **Mopro（現行資産を活用）**、集約は **gnark 継続 or Nova で端末寄せを検証**、
★1を消すなら **Noir** を段階導入。まず「手法(層2エンジン・層3集約)」を決め、その後にこの表で乗り物を選ぶ。
