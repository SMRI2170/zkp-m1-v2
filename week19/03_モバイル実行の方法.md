何が必要か**を具体的に示す。手法とメリデメは [01_手法の全体像.md](01_手法の全体像.md) /

## 0. 前提 — 「モバイルでZKPをやる」とは何をすることか

```
端末でやること: 入力 → witness生成 → proof生成          （重い＝ここが本題）
端末外でやること: verify（軽い。普通はチェーン/サーバ、端末でも可）
```

つまりモバイル化＝「**証明生成器(prover)を端末で動くバイナリにして呼び出す**」こと。方法は2系統:

- **ネイティブ**: prover を **arm64 にクロスコンパイル**して呼ぶ（速い。本命）
- **WASM**: prover を WebAssembly にして呼ぶ（移植は楽だが**ネイティブ比 3.5〜4倍遅い**）

### 共通で効いてくる制約
- **RAM が支配的**: 3GB以上のRAMで安定（FibRace実測）。回路が大きいほどメモリを食う
- **iOS シミュレータは基本不可**、**Android は arm64 実機/エミュ**（x86_64エミュ不可のことが多い）
- **witness生成 と proof生成 は別物**: witness を軽くする専用ツール（witnesscalc等）があると効く
- Flutter からの呼び出しは **dart:ffi（ネイティブ .so/.a を直接叩く）** か **プラグイン** が基本

---

## 1. Flutter への繋ぎ方（3パターン）

| 方法 | 中身 | 向き |
|---|---|---|
| **Mopro の Flutter パッケージ** | prover を Swift/Kotlin/Dart バインディングに自動生成 | **最短・推奨** |
| **自前 FFI（dart:ffi）** | arm64 の `.so`(Android)/`.a`(iOS) を自分で作り Dart から呼ぶ | 細かく制御したい時 |
| **MethodChannel プラグイン** | ネイティブ側(Kotlin/Swift)に実装し channel 越しに呼ぶ | 既存ネイティブ実装がある時 |

※ あなたの現行アプリは rapidsnark を端末で動かしており、③に近い構成。Mopro に寄せると①で標準化できる。

## 2. フレームワーク別・モバイル実行方法

### 2-1. circom + rapidsnark（現行）
- **モバイル化**: rapidsnark は C++/arm64 アセンブリで**元から端末向け**。`.zkey` と witness計算器を同梱し呼ぶ。
- **witness**: `witnesscalc`(C++) で高速化（wasm witnessより速い）。
- **Flutter**: Mopro の `circom` アダプタ＋`mopro_flutter_package`、または既存の FFI/プラグイン。
- **性能**: 約11.8k制約(実測)なら実機で秒未満〜数秒。
- **注意**: `.zkey`（回路別セットアップ産物）をアプリに同梱する必要。回路更新＝再セレモニー＋再同梱。
- **判定**: **今すぐ動く。Mopro で標準化するのが楽**。

### 2-2. Noir + Barretenberg
- **モバイル化**: バックエンド `bb` を **arm64 ネイティブ**で使う（WASM版もあるが遅い）。`noir-rs`/Mopro が包む。
- **Flutter**: Mopro の `noir` アダプタで Swift/Kotlin/Flutter バインディング生成。
- **性能**: クライアント証明が速い部類。準備(SRS)は1回で使い回し＝アプリ同梱物が回路更新に強い。
- **注意**: 回路を Noir へ移植。**検証はオンチェーンで gas 高め**（端末側の話ではないが設計に響く）。
- **判定**: **モバイル証明は◎**。セットアップ根治狙いならこの経路。

### 2-3. halo2
- **モバイル化**: Rust なので **arm64 にクロスコンパイル**。Mopro が halo2 プローバのモバイル生成に対応。
- **Flutter**: Mopro 経由でバインディング。
- **性能**: 回路次第。KZG は universal SRS を同梱、IPA は準備不要。
- **注意**: **回路実装(chip/gadget)が難しい**のが最大の壁。モバイル化自体より回路作りが重い。
- **判定**: モバイルには載るが、**開発コストが高い**ので特別な理由がなければ後回し。

### 2-4. Plonky2 / Plonky3
- **モバイル化**: Rust → arm64 クロスコンパイル。セットアップ不要でバイナリが素直。
- **Flutter**: FFI で `.so`/`.a` を呼ぶ（専用の成熟プラグインは少なめ、Mopro のarkworks系枠を利用）。
- **性能**: 証明生成は速いが、**証明が大きくメモリを食いやすい**。
- **注意**: 現行 EdDSA(BN254系)と**体が違い非ネイティブ演算で重い**。端末回路には不向き。
- **判定**: 端末の per-witness 証明には不向き。**集約を端末側でやる実験**なら候補。

### 2-5. Nova / Sonobe（Folding）
- **モバイル化**: Rust(arkworks) → arm64。**省メモリなので端末で回しやすい**のが最大の利点。
- **Flutter**: FFI で呼ぶ（専用プラグインは発展途上、自前FFIが現実的）。
- **性能**: 1ステップずつ畳むためピークメモリが小さい＝**弱い端末でも集約が回る可能性**。
- **注意**: ステップ回路へ再設計。最終圧縮の証明系を別途用意。事例が少なく自作要素が多い。
- **判定**: **「複数端末を端末側で1つに畳む」用途に最も向く**。研究的だが本案件の集約と相性良し。

### 2-6. RISC Zero / SP1（zkVM）
- **モバイル化**: 技術的には Rust を arm64 化できるが、**証明生成が重くスマホには過大**。
- **実運用**: 端末は入力送信のみ、**リモートprover(サーバ/GPU)**が証明を作る形が現実的。
- **Flutter**: 端末側はAPI呼び出しだけになりがち（＝オンデバイス証明にならない）。
- **判定**: 今のモバイル単独証明には不向き。将来の高性能端末/用途で再評価。

### 2-7. Cairo / Stwo（Starknet）
- **モバイル化**: **モバイル実機での証明実績が最も豊富**（FibRace で多数機種が5秒以内）。Swift/Kotlin SDK。
- **Flutter**: Starknet 系モバイルSDK 経由。
- **性能**: Poseidon が速く、端末証明は良好。セットアップ不要。
- **注意**: **検証が Starknet 前提**で、現行 EVM＋gnark と土台がずれる。
- **判定**: モバイル証明そのものは優秀。だが**エコシステム乗り換え**が必要で本案件とは不整合。

### 2-8. gnark（Go）
- **モバイル化**: `gomobile` で iOS/Android ライブラリ化は可能だが、**証明生成が重く端末向きでない**。
- **判定**: **集約サーバとして継続**が正解。モバイル証明器としては使わない。

### 2-9. Mopro（橋渡しツールキット）
- **役割**: 証明系そのものではなく、**上記(circom/halo2/Noir/arkworks)を iOS/Android/Flutter/RN の
  バインディングに変換**する。
- **できること**: 現行 circom 回路を**そのまま**モバイル化、後から Noir/halo2 へ差し替えも同一手順。
- **注意**: iOS シミュレータ非対応 / Android は arm64。中で選んだ証明系の性質（gas・準備）はそのまま。
- **判定**: **どの証明系を選んでも、モバイル配布はこれで一本化するのが楽**。

## 3. まとめ表（モバイル実行の観点）

| FW | 端末証明 | モバイル化の方法 | Flutter連携 | 端末の重さ | 一言 |
|---|---|---|---|---|---|
| circom+rapidsnark | ◎ | 元からarm64ネイティブ | Mopro / FFI | 軽 | 今すぐ動く |
| Noir+bb | ◎ | bb をarm64ネイティブ | **Mopro(Flutter)** | 軽〜中 | 準備不要・速い |
| halo2 | ○ | Rust→arm64 | Mopro | 中 | 回路作りが重い |
| Plonky2/3 | △ | Rust→arm64(FFI) | 自前FFI | 中〜重 | 体不一致で不向き |
| Nova/Sonobe | ◎(省メモリ) | Rust→arm64(FFI) | 自前FFI | 軽 | 端末側集約向き |

| gnark | ✕ | gomobile(重い) | — | 過大 | 集約サーバ専用 |
| Mopro | — | 上記を包む | **◎公式Flutter** | — | 配布を一本化 |

## 4. あなたの Flutter アプリへの当てはめ（結論）

1. **今の circom 回路をモバイルで堅くする** → **Mopro の circom アダプタ＋`mopro_flutter_package`**。
   回路・検証・集約を変えずに端末証明を標準化（現行の自前構成からの移行が最小）。
2. **★1セットアップを消しつつ端末で速く** → **Noir+bb（Mopro Flutter経由）**。回路をNoirへ移植。
3. **複数端末を端末側で1つに畳む実験** → **Nova/Sonobe を FFI で**（省メモリが効く）。
4. **集約はサーバのまま**なら **gnark 継続**（モバイル化しない）。

共通指針: **端末証明は Mopro で一本化**し、証明系（circom/Noir）は段階的に差し替える。
検証は当面オンチェーン（Groth16なら安い）を維持。RAM 3GB未満の端末は要注意。

## 5. モバイル実装の難易度（実装の観点でのまとめ）

難しさは「回路の書きやすさ」ではなく **「証明器を端末に載せて呼べるか＝arm64バイナリ化＋Flutter連携」**
で決まる。回路自体はどれも小さく（実測: circom フル 11,785制約 / Noir 2,953ゲート）、
**証明が回るか自体は問題にならない**。分岐点は **Mopro が公式対応しているか**。

| FW | モバイル難易度 | 理由 |
|---|---|---|
| circom + rapidsnark | ★☆☆ 易 | 元からarm64、**Mopro公式Flutter対応**、現行アプリが近い構成 |
| Noir + bb | ★☆☆ 易 | bbにモバイルビルド、**Mopro公式Flutter対応**（本検証で proof→verify 確認済） |
| Cairo / Stwo | ★★☆ 中 | モバイル実証は豊富だがSDKがStarknet系＝土台の乗り換えが要る |
| halo2 | ★★☆ 中 | Rust→arm64はMopro対応。ただし**回路実装(chip/gadget)が難しい**のが本当の壁 |
| Plonky2 / Nova | ★★★ やや難 | Rust→arm64は可だが**Flutter用の成熟プラグインが無く自前FFI**が必要 |
| gnark | ★★★ 難(非現実的) | gomobileで載るが証明生成が重くサーバ向け |
| RISC Zero / SP1 | ★★★ 難(非現実的) | 端末単独では重すぎ、**リモートprover前提**でオンデバイスにならない |

**分岐点＝Mopro**: 公式対応は **circom / halo2 / Noir** の3つ（iOS/Android/**Flutter**バインディング自動生成）。
この3つは「易」。Plonky2/Nova は dart:ffi で自前配線＝やや難。gnark/RISC Zero は端末証明に不向き。

→ **本案件の現行 circom も、試した Noir も「易」グループ**（両方 Mopro Flutter に載る）＝モバイル化リスクは低い。
難しくなるのは Plonky2/Nova を端末で使う場合（集約の端末寄せをやるなら、ここだけ自前FFIの覚悟が要る）。
