# Pi受信の電源投入時自動起動

## 構成

ユーザーの明示依頼に基づき、手動・期間限定のrun／fastとは別に、受信専用systemdサービス `zkp-rid-observer.service` をA/B/Cへ導入した。OS起動時にネットワークとwlan0のupを待ち、60秒単位の受信を繰り返す。SSHログインや端末からの実行操作は不要。送信・hostapd・monitor切替え・sudoers変更は含めない。今後のobserver-d/e/fもインストーラ・設定読込に追加したが、追加予定の機材は未導入。

一般ユーザーpiとCAP_NET_ADMINで既存のスキャンキャッシュ受信コードを呼ぶ。時刻・RSSI・生Vendor内容を各PiにJSONLと文字列で逐次保存。既存データ・旧release・個別マーカー設定を保持する。これは機体・観測者ハードの真正性を保証しない研究用PoC。

## 保存と状態確認

```sh
systemctl is-enabled zkp-rid-observer.service
systemctl status zkp-rid-observer.service
cat ~/zkp-beacon-observer/current/captures/boot-status.json
```

保存先：`~/zkp-beacon-observer/current/captures/observer-X/<日時>/`。observations.jsonl／observations.txt／events.jsonl／summary.json。ディレクトリ0700、ファイル0600。currentは版管理されたreleaseへのリンクで、旧release配下のcapturesも削除しない。生データ・受信機接続先・識別子・boot IDはGitへ含めない。

## 運用上限

| 項目 | 設定 |
|---|---|
| 起動 | network-online後、wlan0がupになるまで15秒ごとに待機 |
| 収録 | 60秒分割、スキャン要求1秒、キャッシュ読出し0.25秒 |
| 周波数 | 特定チャネルへ固定せず、ドライバ対応チャネルを要求 |
| 子プロセス | 仮想アドレス空間128MiB、1ファイル20MiB |
| サービス | MemoryMax160MiBを要求、CPUQuota50%、TasksMax32 |
| ホスト余裕 | MemAvailable192MiB・ディスク空き512MiB未満で停止 |
| 保存量 | 次区間の予約64MiB込み256MiB／1万ファイルに達する前に停止 |
| 障害 | 3区間連続失敗で終了、systemd再起動は30秒待機・5分に3回まで |
| 上限停止 | 終了78は自動再起動しない。回収・空き容量確保後に手動再開 |

メモリcontrollerがないカーネルではcgroup上限の実効性は別問題。設定値だけを実測上限と扱わず、利用可能な計測を集計JSONに残す。短い区間を積み重ねる構成なので区間間に起動処理の空白があり、全パケットを取り切る保証はない。

JSONLは逐次flushするが、突然の電源断直前の永続性を保証しない。通常はOSのシャットダウン後に電源を外す。受信中の同一Wi-FiでのSSHはスキャンによって遅れる場合がある。接続遅延をメモリ不足と断定しない。

```sh
sudo systemctl stop zkp-rid-observer.service
sudo systemctl disable --now zkp-rid-observer.service
sudo systemctl restart zkp-rid-observer.service
```

stopは現在の60秒区間の自然終了を待つため、完了に最大約95秒かかる場合がある。自動受信が動いている間はfast等の別の能動スキャンを重複開始しない。

## 検証と限界

全転送ファイルのSHA-256を照合し、systemd-analyze verify後にenable --nowを実行。再起動検証は1台ずつ行い、前後のboot ID変化、enabled、active/running、受信開始状態を確認する。A/B/CすべてでOS再起動によるboot ID変化とログインなしのサービス起動を確認。最終照会では全台enabled・active/running・NRestarts=0、保存先の権限違反0。受信対象を送信していないため観測行は0件。Aではサービス全体の現在メモリ約38.1MiBを取得、B/CのMemoryCurrentは未取得であり0に置換しない。各Piの既存Wi-Fi合成テスト21件も成功。

詳細な実行結果は[集計JSON](results/pi-boot-20261113/validation.json)を参照。

ローカルのPi関連Python30件、既存UAV88件、Go、contracts48件成功。自動受信の容量・メモリ余裕の判定、無制限再起動の抑制、権限・書込み範囲、unit設定へのパス注入拒否、6ノード名をテストした。

既存Wi-Fi接続設定・パスワード・sudoersを変更していない。再起動中にSSH制御接続が終了したため、保存済みのホスト鍵で再認証して継続した。短いkeepaliveで切れた制御接続を受信プログラムの停止と混同しない。再起動テスト制御プログラムは途中で旧接続を参照して一度終了したため、検証済みAを繰り返さず、残りのノードだけ再開した。

再起動検証後、状態ファイルの一時名を毎回変えて、中断した書込みを残したまま次回起動できるよう補強した。停止時の状態表示もSTOPPEDと有限テスト完了を区別した。管理下の既存unitは内容を照合してバックアップ後に更新し、認識できないunitは上書きしない。初版でA/B/Cの再起動確認を行い、補強した最終版は全台で起動確認、Bで再度OS再起動を検証した。

この作業では管理された試験電波やM350の送信を開始していない。サービス稼働や空の収録ファイルの生成を、実ドローンの受信成功として数えない。電源の物理的な抜き差し、容量満杯までの書込み、実機メモリ枯渇、ネットワーク切断注入、長期運用、同一送信の多局対応付けは未実行。

## 根拠

[systemd.service公式](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)と[systemd.exec公式](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)を確認して構成した。ネットワーク依存順だけでは接続完了を保証しないため、受信ループでもインターフェース状態を待つ。
