# E受信ノードの初期導入と実機受信確認

2026-11-14実施。研究用PoC。ZKPなし。機体認証・DRIP検証・センサ真正性の保証ではない。

## 導入したもの

EはRaspberry Pi 3 Model B Plus Rev 1.3。64bit（aarch64）、Debian GNU/Linux 13 (trixie)で起動・SSH接続を確認した。
受信サービスは未導入だったため、既存のPi受信キットをハッシュ検証付きで新しい版管理releaseへ配置した。

- `zkp-rid-observer.service`をenabled/activeに設定。送信サービスは導入していない。
- ポーリング0.25秒、スキャン要求0.25秒、30秒ごとの全チャネル探索を含むadaptive受信。
- JSONLと読み取り用TXTに、時刻・RSSI・周波数・生Vendor IE・解析結果・送信元分類を保存。
- 解釈できないOpenDroneID候補も生情報と解析理由を保存する既存処理を使用。任意の未対応方式を受信・解析できるという意味ではない。
- Pi研究IDは`onboard_pi`に分類。実際のDJI機のIDは未登録で、未登録IDを自動でDJI機と断定しない。
- 保存上限・空きメモリ／ディスクの停止ガード、所有者のみの保存権限を維持。

A・B・C・D・Fの設定やアプリのDBは今回変更していない。Aの既存Beaconを試験用に受信した。
個体設定、IP、実座標、生受信、認証情報は非公開capturesに保持し、Gitへ追加しない。

## 実電波による確認

Aの予備BeaconをEが受信した。Aの位置は実GPS、Beaconの識別用IDは研究用Pi IDであり、実DJI機のRemote ID試験ではない。
初期照合では受信76件がAの直近送信Vendor IE内容と一致し、全件で位置・RSSI・GPS高度・気圧高度の存在を確認した。
これは同じ内容の照合であり、物理的に同一の無線パケットを特定したという意味ではない。

完了済み60秒セグメント1本の受入試験：

| 項目 | 結果 |
|---|---:|
| 保存件数 | 122 |
| 時刻・RSSI・生Vendor IEあり | 各122 |
| Pi送信としての分類 | 122 |
| CSV／JSON書き出し行数 | 各122 |
| スキャン要求／受理／失敗 | 169／163／6 |
| キャッシュ更新間隔の中央値 | 約0.283秒 |
| 更新間隔の95百分位 | 約0.850秒 |
| 最大更新間隔 | 約7.938秒 |
| 受信子プロセスの最大RSS | 25,608 KiB（約25.0 MiB） |
| 検査時の利用可能メモリ | 568,296 KiB（約555 MiB） |
| 受信終了コード | 0 |

122件は新しいLinux受信キャッシュ記録であり、122個の独立した無線パケット数を保証する値ではない。
0.25秒はスキャン要求周期であり、受信周期や欠落なしの保証ではない。スキャン失敗割合をRFパケット損失率と呼ばない。
今回の最大間隔の原因を個別に確定する追加実験は未実施。

集計：[summary.json](results/observer-e-setup-20261114/summary.json)。実座標や生データは含めない。

## 保存・書き出しと検証

生受信はPi上の`~/zkp-beacon-observer/current/captures/observer-e/<run>/`にJSONL/TXTで保存される。
完了済みセグメントから既存`export_observations.py`でCSVとJSON配列を生成し、元JSONL・CSV・JSONで122件が一致した。
CSVには生JSONと生Vendor IEも残る。これらの実ファイルはPi内の所有者限定capturesに保持した。

書き出しの最初の試験は、受入試験スクリプトが作った親ディレクトリに他ユーザー向け権限が残り、既存のプライバシーチェックが拒否した。
既存の検証を弱めず、この試験専用ディレクトリを0700に修正し、再試験はumask 0077で実施した。
その後、captures配下の全ファイル・ディレクトリにグループ／その他のアクセス権がないことを確認した。最初の失敗ログも非公開領域に残した。

E実機上のPi Pythonテスト52件は全成功。導入時の同梱Wi-Fiテストも成功。
`systemctl is-enabled/is-active zkp-rid-observer`はenabled/active、確認時の再起動回数は0。
NTP同期フラグはyesだが、観測時刻の精度や局間同期誤差は独立計測していない。
受信機の実座標は未設定。現地での位置合わせが必要。

## メモリ制御と残件

Eのcgroup controllerにはmemoryがなく、systemdの`MemoryMax=160M`設定による実効的なメモリ制限は確認できない。
`MemoryCurrent`も取得不能だった。設定値だけを根拠に160MiB以内に制限されると主張しない。
受信ラッパーの子プロセスには別途128MiBのアドレス空間制限があり、開始前に192MiB以上の空きメモリを確認する。
今回のRSSは約25MiBだったが、長時間・高密度環境のOOM耐性は未検証。カーネル設定や起動パラメータは変更していない。

未実施：物理的な電源再投入後の自動起動確認、実Matrice 300/350受信、飛行・長時間・混雑環境、現地位置合わせ、独立した時刻精度評価。
通常の受信は試験終了後も継続。収録上限に達した場合は自動削除せず停止する既存方針を維持する。
