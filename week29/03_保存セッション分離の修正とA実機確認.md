# 保存セッション分離の修正とA実機確認

## 修正したこと

旧ログで容量上限に達したAが、電源を入れ直しても同じ保存先を判定して停止していたため、保存の単位を変更した。

| 項目 | 修正後 |
|---|---|
| 保存先 | 役割ごと、プロセス開始ごとのUUIDセッションへ分離 |
| 再起動 | 全役割で新セッションを作り、以前のデータを保持 |
| 受信の予算 | 自分の現行セッションだけを計算。センサ・送信ログを加算しない |
| セッション容量 | 受信1GiB、センサ1GiB、予備送信512MiB |
| SD全体 | 最低1GiBを予約。受信は次区間64MiB分も追加予約 |
| その他の保護 | 10,000ファイル上限、メモリ・CPU・単一ファイルの既存制限を維持 |
| 上限到達 | 終了コード78で停止。自動再試行で予算をリセットしない |
| 同時起動 | 同じ役割のwriter lockで拒否 |
| 削除 | 旧記録の自動削除・上限到達時の自動ロールオーバーなし |
| 時刻 | セッションmanifestにboot ID・UTC・起動後時刻、送信JSONLにもUTCを追加 |
| 状態 | 保存件数、最終書込み、セッション使用量、上限、停止理由をJSON表示 |

予算は旧履歴のセンサ約19.39MiB/時・送信約9.65MiB/時を基準に、準備中の蓄積にも余裕を持たせた初期値。新送信行はUTC等を追加して大きくなっているため、旧書込み速度だけで長時間動作を保証しない。受信量・周囲の電波環境も別に評価する。

### 受信データが実際に保存できるか

通常受信を一時停止し、同じAの無線機で、明示的に未解析Wi-Fi保存を有効にした15秒の診断収録を実施した。権限付きの時間制限付きサービスを使い、終了後に通常受信を再開した。

- 保存159行、RSSIあり159行、受信UTCあり159行、起動後観測時刻あり159行。
- 全159行は通常Wi-Fiの候補。Remote ID・実ドローンとしては確認していない。
- 通常のRID受信サービスは、確認時点ではRID保存0件で受信待ち。通常運用の未解析Wi-Fi保存設定を勝手にONにはしていない。
- この結果を、Matriceの実受信成功や全パケット受信率へ置き換えない。

## ACTランプの表示

対応するPiで明示的に導入する任意機能。Aでは導入・動作確認済み。PWRランプは変更しない。

| 点滅 | 意味 |
|---|---|
| 約0.9秒ON／0.9秒OFF | 必要な収録処理のheartbeatと書込み状態が整合 |
| 約0.1秒ON／約1.9秒OFF | 起動中、またはRID観測待ち |
| 約0.1秒ON／0.1秒OFF | 停止・上限・古いheartbeatなどの異常 |

Aのセンササービスを意図的に停止し、異常時の0.1秒ON/OFFとFAULT判定を確認した。その後センサを再開し、再起動試験も実施した。

ランプは**収録プロセスの状態**を示す。GPSの精度、機体の真正性、RIDの連続到着を保証しない。状態のboot IDが前回起動のもの、またはheartbeatが古い場合は正常表示しない。

LED制御は別サービスに分離し、無線capability・ネットワーク・capture書込み権限を与えない。ACTのsysfsだけに書込みを許可し、停止時は元のtriggerへ戻す。センサの`dialout/i2c`、受信のCAP_NET_ADMIN、送信の既存無線capabilityを拡大していない。

## 6時間の継続監視

4時間の実験を上回る6時間の監視プログラムをA上で起動した。チャットで待つ方式ではなく、systemdの時間制限付きサービスが状態・保存件数をJSONLへ残し、終了時にsummary JSONを作る。異常を3サンプル確認した場合は早期終了して失敗を記録する。

**開始を確認した段階で、6時間完走は未確認。** 短時間の動作確認を長時間試験の成功とは報告しない。監視プログラムの補強のため、最初の監視を短時間の事前試験として停止・保持し、補強版で6時間監視を開始し直した。収録サービスはこの切替えで停止していない。

監視は受信待ちを明示的に保持し、受信成功に数えない。監視用プロセスのCPU・RAM・実行時間も制限する。データは新releaseの`captures/soak-*`配下。ローカルのprivate receiptに実際のパス・unit名を残している。

## 残っている確認

- 物理的な電源OFF/ONによるコールドブート試験は未実施。今回確認したのはOSの再起動。
- 6時間完走、実Matrice受信、飛行中のGPS/RSSI収録は未確認。
- 過去の低電圧警告への物理対策は別途必要。現在のフラグ0を過去の電源品質改善の証明にはしない。
- A以外のノードへの新コード配布は未実施。コードは共通化したが、他ノードが更新済みとは報告しない。
- 空き不足や上限で停止した場合の旧記録の回収・整理は引き続き必要。無制限保存にはしていない。
