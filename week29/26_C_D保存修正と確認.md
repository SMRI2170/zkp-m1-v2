# C・D：保存修正の実機適用（2026-11-18）

## 対象と手順

ユーザーによるC・Dの接続後、保存済みSSHホスト鍵とノード識別情報を照合して作業した。シャットダウン済みB・E・Fへの操作は行っていない。

接続時、Cの収録サービスはactive、Dは終了コード78でfailedだった。終了コードだけでは過去の停止理由を確定できない。

1. RAM・SDの余力、設定、旧サービス定義を確認する。
2. 収録を正常停止し、全releaseのcaptureと設定を保全する。
3. アーカイブをMacへ回収して集合・サイズ・SHA-256を照合する。
4. 別releaseに新コードを配置し、実機テスト成功後にreceiver専用で有効化する。
5. 設定の保持・新セッション・旧ファイル全件のハッシュを確認する。
6. OS再起動後の自動収録と、時間制限付き監視を別途確認する。

手順・保存制限の仕様は[B・E・Fの報告](25_B_E_F保存修正とOS再起動確認.md)と共通。Pi関連ソース46ファイルが使用するkitとローカルコードで一致することを確認した。stageテストの一時領域にはSDを使用し、容量ガードやテストを弱めていない。

## 結果の確認先

両台とも実機上のPi関連58テストに成功し、修正版の新セッションで収録を開始した。全旧ファイルのハッシュと設定ハッシュが更新前と一致することを確認した。

| ノード | 保全・照合ファイル数（設定含む） | 元データ合計 | 更新後 |
|---|---:|---:|---|
| C | 5,276 | 274,928,221 bytes | active・新セッション |
| D | 1,605 | 202,680,240 bytes | active・新セッション |

有効化直後の対象RID記録は両台とも0件。これは実ドローンの受信成功を示す結果ではない。

実行済みの更新結果は[匿名集計JSON](results/cd-storage-repair/summary.json)を参照。

両台ともOS再起動を実施し、boot IDの変更・現在bootに属する別セッション・同じrelease／設定・enabledかつactiveの収録サービスを確認した。[再起動結果](results/cd-storage-repair/reboot-summary.json)。再起動確認時の対象RID記録は0件。

5分で終了するreceiver専用監視を開始した。[開始記録](results/cd-storage-repair/monitor-start.json)。監視はSSH切断後もsystemdで継続し、360秒の実行上限を持つ。ホストRAM・SD空き・収録heartbeatをCSV／JSONへ記録する。サービス単体のMemoryCurrentが得られない場合は欠測として扱う。

その後の自動回収で、両台とも300秒完走・収録health FAULT 0を確認した。Cは17サンプル、Dは18サンプルで、最終状態は両台WAITING。[5分監視集計](results/cd-storage-repair/monitor-collection-1/summary.json)。対象RID受信成功ではない。

次に[4時間監視](27_C_Dの4時間収録監視.md)を開始した。4時間試験は未完了であり、5分試験と区別する。

生ログ、アーカイブ、manifest、設定、認証済み接続情報はignored captures配下の0700／0600領域に保存。私的保存先の参照は`.cache/week29-issue97-live-cd-root`。実測座標・送信ID・鍵・認証情報は公開集計に含めない。
