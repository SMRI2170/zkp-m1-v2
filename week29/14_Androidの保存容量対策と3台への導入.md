# Androidの保存容量対策と3台への導入

ユーザー依頼「Aノードのようにデータ量でエラーになり記録を失う状況を避けたい」に対し、Android受信アプリを`0.14-segmented-storage`へ更新した。関連：[#90 保存停止原因](https://github.com/SMRI2170/zkp-m1-v2/issues/90)、[#84 Android受信基盤](https://github.com/SMRI2170/zkp-m1-v2/issues/84)。

## 修正したこと

旧版は観測・GPS・診断を1つのSQLiteに蓄積し、本体64MiB・各テーブルの行数制限で停止した。Pixel 8の保全コピーは64MiB・空きページ0で、保存余裕がなかった。ただし、その最終停止原因をSQLiteFull例外の直接確認まで行ったわけではない。

新しい版は以下の構成にした。

| 保存先 | 動作 |
|---|---|
| 旧`database/observations.sqlite` | 読み取り専用で保持。旧v1も移行・上書きせず読める |
| `database/segments/segment-<連番>-<UUID>.sqlite` | 新しい記録。48MiB手前または観測・GPS・診断の合計8万行で次へ切替 |
| 各分割DB | ハード上限64MiB。キュー最大256件を維持 |
| DB保存先全体 | 1GiB・最大64分割。端末の空き512MiBを確保する条件で書込み |
| `database/storage-status.json` | 稼働・切替・停止理由、容量、UTC・monotonic・boot_scopeをDB外へ記録 |
| 任意の追加JSONL | 20MiB単位で切替。合計512MiB上限では追加JSONLだけを止め、DB記録は継続 |

有限の上限や実際の空き容量不足に達した場合は、既存データを削除せず停止理由を表示する。通知許可がある場合は停止通知も出す。全件JSONL/CSV書き出し・最新テキスト・DB件数は旧DBと新しい分割DBを合わせて扱う。

旧DBが満杯であるだけで新しい収録を拒否していた開始時の累計10万行チェックを、新しい保存方式に合わせて撤去した。行数・容量・破損・権限のチェック自体を無効化したものではなく、各分割と全体上限へ移した。観測とGPSの一意キーを過去DBにも照会し、分割・プロセス再起動で同じ観測を再追加しない条件を維持した。

実機RIDのProtocol 0対応、証明の入力許可、ZKP回路、OSのスキャン制限、位置情報権限は今回変更していない。生データを自動削除・切り詰めして継続する処理もない。

## 接続中の3台へ導入

更新直前に、全アプリcaptureを別の非公開ディレクトリへ再保全した。受信サービスが動いていないことを確認し、アンインストール・データ消去をせずAPKを上書き更新した。

| 端末 | Android | 更新前 | 更新後 | 実機テスト | 元の実験ファイル |
|---|---|---|---|---|---|
| Pixel 8 | 17 | 0.10 | 0.14 | 4件成功 | ハッシュ全件不変 |
| Pixel 6 Pro | 12 | 0.13 | 0.14 | 4件成功 | ハッシュ全件不変 |
| 接続中ASUS（device-3） | 7.0 | 0.13 | 0.14 | 4件成功 | ハッシュ全件不変 |

ASUSの最初の通常インストールは60秒でタイムアウトした。端末が旧版のままであることを確認し、`adb install --no-streaming -r`で再試行して成功。最終APKを3台とも同じSHA-256で適用し直し、テストを確認した。

最終確認で、Pixel 8とASUSは導入済みAPKを読み戻したSHA-256も配布セットと一致した。Pixel 6 Proは更新・テスト・元ファイル不変の確認後にADBで見えなくなったため、最後のAPK読み戻しだけは未実行。接続不能を故障や電源断と断定しない。

接続されていないもう1台のASUS（device-2）は未更新。この作業でPi B〜Fへ保存修正を導入したという意味でもない。

## 実際に通したテスト

各端末の`FieldTestInstrumentation`は、実験用DBとは別の`captures/test-*`だけを使う。合成テストをフィールド証拠に混ぜない。

1. **満杯の旧DB保持**：合成paddingでSQLiteFullが発生するまで旧DBを埋め、新DBへ観測・位置を書けること、旧DBのSHA-256・スキーマ・内容が不変なことを確認。
2. **自動切替と再起動**：テスト用に小さくした分割条件で複数DBを生成し、全件書出し・跨DB重複排除・プロセス相当の再オープン・整合性・権限を確認。
3. **全体容量停止**：合成的に小さくした全体予算で新規書込を拒否し、`STOPPED_ARCHIVE_LIMIT_REACHED`がDB外へ記録され、読出し可能なまま停止することを確認。
4. **追加JSONL境界**：小さい合成セッションを上限まで書き、予約領域で終了理由を保存し、別セッションを作って旧ログを残せることを確認。

Android/JVM共通テストは各50件、Python補助ツール19件、APK/テストAPKビルド・Lintが成功。関連する既存チェックはUAV88件、Go、contracts48件が成功した。

`smoke_device_persistence.py`も分割DBを含めて保全・比較するよう更新した。旧DBだけを見て「新しい記録がない」と誤判定しない。ソースDBごとのIDを保持した派生比較DBを作り、原本DBを残す。比較もSQLと小さい解析レコードで行い、大量の過去JSON全体をPythonのリストに複製しない。

## 未実行・限界

- Pixel 8の通常画面からの3フェーズ収録Smoke testは、画面ロックで開始できなかった。ロック解除を依頼済みで、回避操作はしていない。フェーズは0件で、通常収録の成功とは報告しない。
- 実際の容量不足時の画面・通知の故障注入、実際に端末空きを512MiBまで減らす試験、4時間以上のフィールド連続運転は未実行。
- 1GiBは無制限保存ではない。未知Wi-Fi候補を大量保存する設定では早く達し得る。次回実験の必要容量・持続時間は実データの保存速度で見積もる必要がある。
- OSがアプリを終了した場合や突然の電源断に、未確定キューまで保持できる保証はない。既存の上限・保護を外して「止まらない」とはしていない。

## 成果物・移行

コードは`experiments/kmp-rid-observer/`。追加した保存制御は`DatabaseSegments.kt`。

```sh
cd experiments/kmp-rid-observer
# Java 17以上と既存Android SDK設定が必要
./gradlew --no-daemon :shared:allTests :androidApp:assembleDebug \
  :androidApp:assembleDebugAndroidTest :androidApp:lintDebug
```

他端末用のコード・APKセットもローカル生成済み：`.cache/week29-storage-field-kit-v14/`。manifestのAPKハッシュが最終導入APKと一致することを確認した。これはdebug/test用であり、リリース鍵や本番配布の保証ではない。

更新前の保全、端末ごとのテスト・インストールログ、実データのハッシュは`captures/week29-android-preupdate-<取得時刻>/`。所有者専用権限・Git対象外で保持する。公開用の検証サマリーとログは`week29/results/android-storage-v14/`に記録する。
