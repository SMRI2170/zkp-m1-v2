# Pixel 8専用アプリ：RSSIによる方向推定とWi-Fi／BLE実機確認

2026-11-02。ユーザーの「既存アプリではなく専用アプリで試す」「厳密AoAでなく推定でもよい」という指示に基づく。新規ネイティブAndroidアプリを作成し、USB接続のPixel 8へインストールした。送信側の位置や電力の真正性、機体認証を保証するシステムではない。

## 1. 作成したもの

- 表示名：**RID方向検証**、パッケージ：`org.smri.ridprobe`。
- [ソース・ビルド・操作手順](../experiments/android-radio-probe/README.md)。既存受信アプリの改名・インストールではない。
- BLE広告とWi-FiスキャンのRSSI、観測時刻、端末姿勢の収集。
- Wi-Fi情報要素（IE）とODID形式候補の構造検査。完全なRIDフィールド検証・署名検証ではない。
- RSSIと方位の調和回帰による**RSSI最大端末方位の推定**。校正後の推定と、別回転データによる誤差記録機能。
- 不十分な点数・回転範囲・方向性を「推定不可」とする処理。位相差AoA、CTEのI/Q、Wi-Fi CSIの取得は実装していない。
- APKビルドと合成数学／構造テスト、公開集計のプライバシーテスト。GitHub Actionsにも新規アプリのビルド・テストを追加。

## 2. Pixel 8で何が動いたか

実機はPixel 8、Android 17、API37。Wi-Fiと位置情報は有効だった。以下は**初回USB試験の記録**であり、機能フラグだけからの推測ではない。

| 確認項目 | 初回実測 | 解釈 |
|---|---:|---|
| BLE広告受信 | 205件 | 通常BLE受信処理が動作 |
| 新しいWi-Fiスキャン時刻の観測 | 14件 | fresh通知かつ未重複の結果に限定 |
| その14件内の情報要素 | 258件 | 情報要素APIからデータを取得 |
| その14件内のVendor IE | 65件 | 一般のVendor IEを取得。RIDそのものとは限らない |
| キャッシュを含む全IE取得 | 833件 | 重複を含むため独立観測833件とは呼ばない |
| キャッシュを含む全Vendor IE取得 | 208件 | 同上 |
| 姿勢観測 | 186件 | 回転ベクトルから端末方位を取得 |
| RSSIと姿勢を対応付けた標本 | 195件（複数対象合計） | 1対象195件、または独立195回ではない |
| Wi-Fi／BLEのRID形式候補 | ともに0件 | この場で未検出。端末非対応・パーサ完全性は判定できない |

| アプリで記録したエラー | 0 | 初回ログ内の範囲 |

初回テストは25秒の枠で開始したが、停止と再開があり、記録された実受信区間は約10.08秒＋1.07秒。**25秒連続受信を確認したとはしない。** 初期版では停止理由とインストール前APKハッシュを記録していなかったため、その点も[集計JSON](results/pixel8-radio-probe-20261102/initial-reception-summary.json)へ明記した。

その後、手動再開に古い自動停止タイマーが干渉しない修正、停止理由・稼働時間の記録、Ranging能力の保持、対象一覧の点数表示を追加した。更新版APKのビルドとインストールは完了。更新版の保存セッションでは能力照会までで、受信開始の記録がないため、受信成功試験として数えない。[更新版の起動・能力照会記録](results/pixel8-radio-probe-20261102/later-launch-summary.json)。続く再試験中にADB接続が失われ、無線ADB接続情報を待つ状態となった。

## 3. Wi-Fi Beaconは難しいのか

**Pixel 8でWi-Fiのスキャン結果とIEを取得する処理は動いた。** 一方、これと任意のBeaconの連続取得、RID受信、AoA推定は別の確認である。

1. Androidスキャン結果はキャッシュやOS側の間引きを含み、Beacon／Probe Responseの情報から作られる。モニターモードで全802.11フレームを捕捉したものではない。
2. 前景アプリでも通常は4スキャン／2分等の制限がある。新規アプリは35秒間隔の要求で、制限を自動解除しない。更新がないときに古いRSSIへ現在の姿勢を結び付けない。
3. 24点以上の方位データを集めるには、Wi-Fiだと約12〜15分かかる場合がある。最初の方向推定試験はBLEを優先する。
4. Vendor IEが取得できても、ODID用のIEが発信されていなければRIDは検出されない。この試験には発信を確認済みのRID送信機と独立した正解方向がなかった。

制限の根拠：[Android公式Wi-Fiスキャン](https://developer.android.com/develop/connectivity/wifi/wifi-scan)、[ScanResult情報要素](https://developer.android.com/reference/android/net/wifi/ScanResult#getInformationElements())。公開の[OpenDroneID対応表](https://github.com/opendroneid/receiver-android/blob/master/supported-smartphones.md)にもPixel 8／Android 14のWi-Fi Beacon受信報告があるが、これは別の端末・OS時点の報告であり今回の実機証拠として流用しない。

## 4. 方向推定の精度について何が言えるか

**実機の角度誤差はまだ言えない。** アプリを動かしたことと、使える精度を得たことを分ける。

今回の処理は `RSSI=a+b cosθ+c sinθ+d×時刻+誤差` という探索用の回帰。端末の向きに対するRSSI最大方位を出す。端末の正面方向と受信利得の最大方向は一致するとは限らないため、既知送信方向との補正校正が必要。校正後はデータを消去し、別の回転で誤差を測る。

採用ゲートの24点・270°・6/8区画・振幅2dB・方向成分R²0.35は仮の品質条件で、角度誤差や95%信頼度の保証ではない。持ち方、遮蔽、マルチパス、端末の磁気方位誤差も影響する。

送信電力が回転中に自由に変わると、その変化を方向性として誤認し得る。数学テストには、電力操作で見かけ上よく当てはまる誤った方向を作る失敗例も含めた。M1の同一送信・複数方向同時観測に置き換えたとはしない。

## 5. この端末の能力照会

更新版アプリが取得した能力：UWBは非搭載、Ranging APIのUWBとBLE Channel SoundingはNOT_SUPPORTED、Wi-Fi NAN RTTとBLE RSSIはENABLED。端末のrotation vectorセンサも取得できた。

これは「Wi-Fi RTTからRIDの到来方向を測定できた」という結果ではない。対応APとの測距セッションやAoAの新規セッションは行っていない。BLE Coded PHY・Extended Advertisingの機能フラグだけでは、特定RID信号の受信成功を主張しない。

## 6. 無線でのビルド・インストール

ビルドはMacで行い、Wi-Fi経由のADBでPixelへAPKを送る構成。USB切断後の確認時点では、接続済みのPixelもmDNSの無線デバッグサービスも見つからなかった。ユーザーへワイヤレスデバッグの接続用IP:ポート、必要なら初回ペアリング情報を依頼した。**無線インストール成功はまだ未確認。**

手順は[アプリREADME](../experiments/android-radio-probe/README.md)を参照。再試験スクリプトに `--device IP:CONNECT_PORT` を指定できる。ペアリング用と接続用ポートを混同しない。IP・ポート・6桁コードはGitへ保存しない。

## 7. 保存・再現・残件

- ソース：`experiments/android-radio-probe/`。Gradleラッパー・設定・Javaコード・テスト・実機試験スクリプト。
- 最新APK：`experiments/android-radio-probe/app/build/outputs/apk/debug/app-debug.apk`。ビルド成果物としてローカル保存、Git対象外。
- 公開集計：`week26/results/pixel8-radio-probe-20261102/`。対象識別子、SSID、MAC、生IE、個別角度、端末シリアルを出力しない。
- 生のJSONL、対象別CSV、private summary、スクリーンショットはignoredのcaptures内、700/600。Gitへ追加しない。
- 数学／フレーミング16項目と、公開集計の境界3テストを実行済み。合成の方向回復テストを実機精度の検証と呼ばない。

次の実測は、無線ADB再接続、更新版の連続受信、既知方向の固定送信機で校正、別回転で評価、保持する位置や持ち方・距離を変えた評価。中央値・90%点の角度誤差と、推定不可の割合を併記して初めて「ある程度の精度」を判断する。

この段階ではZKPやスマートコントラクトを追加していない。署名・証明・履歴保護を加えても、取得された観測が物理的に正しいことや、同じRIDが同じ機体であることは別の課題として残る。
