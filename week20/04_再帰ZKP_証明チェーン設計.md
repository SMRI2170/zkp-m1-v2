# 再帰的 ZKP 設計 ── 前の証明を内包する「証明チェーン」（IVC・方式A/gnark 主軸）

作成日: 2026-07-23（更新: 方式A/gnark を主軸に確定） / 目的: 複数ユーザ・複数ノード(ラズパイ)が
同一ドローンの証明を生成し、**前の人の証明を回路内で再帰検証して内包しながら**検証精度を上げる仕組みを設計する。
関連: week20/02（ZKP要件）、week20/05（内包の詳説）、week19 集約(M2)。

> **方式の確定**: 内包には方式A(再帰検証)と方式B(Folding)がある（week20/05）。本設計は
> **方式A＝gnark 再帰を主軸**（各累積が単体検証可能・BN254/EVM 着地・現行 `aggregator/` の延長）とし、
> **方式B(Nova/Sonobe)は省メモリ代替**として温存する。詳細は §0 の採用方式表を参照。

---

## 0. やりたいこと（イメージの言語化）

> 複数の参加者（スマホのユーザ・ラズパイのノード）が、同じドローンの RemoteID 放送を各自観測し、
> **「前の人の証明」を信頼できる形で受け取り、それを内包した状態で自分の証明を足していく**。
> 参加者が増えるほど、ドローン検証の**精度（確信度）が上がる**。

これは暗号の言葉で **IVC（Incrementally Verifiable Computation）＝逐次的検証可能計算**。
「前の証明を回路の中で検証しながら、新しい観測を1つに畳み込む」内包の仕組み。

**核心**: 「前の人を信頼」ではなく「**前の証明を回路内で検証**」する。だから相手を信頼せずに済む
（改ざんされた証明は検証で落ちる＝数学的な信頼）。

### 採用方式（確定）── 方式A（再帰検証）を主軸、方式B（Folding）を省メモリ代替
内包には2方式ある（詳細は week20/05）。本設計は **方式A を主軸**とする。

| | **方式A：再帰検証（主軸）** | 方式B：Folding（代替） |
|---|---|---|
| 各ステップで前の証明を | **その場で完全検証** | 畳み込む（検証は最後に1回） |
| 中間の累積 | **単体で検証可能**（取ってきて verify 可） | 単体では検証不可 |
| 「チェーンから取ってきて検証」 | **○ 忠実** | △ 最終圧縮まで不可 |
| 共有するもの | **小さな標準証明1個**（数百B〜数KB） | 走行累積（インスタンス＋witness, 数十KB〜MB） |
| 1ステップの重さ | **重い**（検証器を回路内で実行） | 軽い・省メモリ |
| EVM 着地 | **そのまま**（BN254/Groth16） | 最後に wrap が必要 |
| 代表フレームワーク | **gnark 再帰（現行 M2 で使用中）** / Plonky2 / Halo2 | Nova / HyperNova / Sonobe |

- **なぜ A が主軸か**: ユーザの要望「**前の証明を入れて“検証”する**」「**チェーンから取ってきて検証**」に
  最も忠実。各累積が**そのまま単体検証可能な標準証明**なので、許可型チェーンに置いて
  「取得→verify」が成立する（方式B の走行累積は最後まで検証不可）。加えて **BN254/EVM にそのまま着地**でき、
  現行 `aggregator/`（gnark・M2）の資産をそのまま延長できる。
- **方式A の代償と対処**: 各ステップで検証器を回路内実行するため**1ステップが重い**。
  スマホには不向きな場合があるため、**重いステップはラズパイ級ノードが担い、スマホは末端の witness 証明
  （軽い circom/Groth16）だけを出す**という役割分担で緩和する（§6）。
- **方式B（Nova/Sonobe）の温存**: 「各ノードを極力軽くしたい／連鎖が非常に長い」場合の**省メモリ代替**。
  ただし中間が単体検証不可なので「取ってきて検証」の像とはズレる。**PoC で A と実測比較**して最終判断。

## 1. なぜ「チェーン（内包）」か ── 2つの集約トポロジ

| | 木構造の並列集約（現行 M2） | チェーン（本設計・IVC/Folding） |
|---|---|---|
| 形 | 集約器が N 個の証明を一度に検証 | 参加者が順に「前の証明＋自分の観測」を畳む |
| 誰が | サーバ（gnark 一括再帰） | 各参加者 / ラズパイ（gnark 再帰を逐次実行） |
| メモリ | N に比例しがち | **1ステップ分だけ（省メモリ）** |
| 「前を内包」 | しない（並列） | **する（逐次内包）** ← ご要望に忠実 |
| 弱点 | サーバ集中 | 途中で誰かが止めると途切れやすい |

→ ご要望（前の証明を内包・分散・精度を積み上げ）には**チェーン(IVC/Folding)が合う**。
ただし脆さ（後述の検閲/途切れ）への対処が設計の肝。

## 2. アーキテクチャ（証明チェーン）

```
参加者1: 観測 → acc1 (自分の整合を折り込んだ累積状態＋証明)
   │  (acc1 を共有)
参加者2: acc1 を回路内で検証 + 自分の観測 → acc2  （acc1 を内包）
   │
   …
参加者N: acc_{N-1} を検証 + 自分の観測 → acc_N   （全員を内包）
   │
最終圧縮: acc_N を 1つの SNARK に圧縮 → ブロックチェーンで1回検証 → trusted / spoofAlert
```

- 各ステップは「前の累積状態 z_{i-1} と証明 π_{i-1}」を入力に、「新しい z_i と π_i」を出力。
- z（累積状態）が参加者をまたいで**成長**する（consistent_count が増える等）。

---

## 3. ステップ回路（各参加者が回路内で強制すること）

**入力**
- 公開: 前の累積状態 z_{i-1}（下記）、前の folded インスタンス（Folding 検証対象）
- 非公開: 新 witness のプライベート値（自分の座標・RSSI サンプル・端末署名 等）

**回路内チェック**
1. **前の証明/インスタンスが正しい**（Folding の検証を回路内で実行）＝前を内包
2. **同一ドローン・同一時間窓**: `drone_id_commitment` と `time_bucket` が z_{i-1} と一致（全員同じ放送）
3. **登録端末である**: 新 device の pubkey が登録集合の Merkle メンバー（#3a Sybil 対策）
4. **二重計上でない**: 新 device が `included_acc`（既参加者集合）に未包含
5. **RSSI 整合を計算**: 幾何距離 d_claim と RSSI 実測 d_meas の相対整合 → `consistency_ok(1/0)`
6. **状態更新**: consistent_count += ok, suspicious_count += (1-ok),
   included_acc に device を追加, step += 1

**出力**: 更新後の累積状態 z_i と証明 π_i

---

## 4. 累積状態（accumulator z）が持つもの

| フィールド | 役割 | 変化 |
|---|---|---|
| `drone_id_commitment` | 対象ドローンの束縛 | 固定（不変） |
| `time_bucket` | 同一時間窓の束縛 | 固定（不変） |
| `consistent_count` | 整合した端末数 | 成長 |
| `suspicious_count` | 矛盾した端末数 | 成長 |
| `included_acc` | 参加済 device 集合（Merkle根 or ハッシュ集合） | 成長（二重計上・Sybil防止） |
| `step_count` | 参加者数 | +1 |

→ 座標・生 RSSI は**回路の外に出さない**（秘匿）。公開されるのは上記の集計だけ。

## 5. 前の人の証明をどう共有するか（設計）

### 5.1 何を渡すか（方式A：標準証明1個 ／ 方式B：走行累積）

**方式A（主軸）── 渡すのは「小さな標準証明 π_{i-1}」1個**
- **公開状態 z_{i-1}**: drone_id_commitment / time_bucket / consistent_count / suspicious_count /
  included_acc（参加済集合）/ step。数百バイト級で小さい。
- **証明 π_{i-1}**: 「z_0 から z_{i-1} まで正しく1ステップずつ進めた」を保証する**単体検証可能な Groth16 証明**
  （BN254, 約200バイト）。次のノードは **この π_{i-1} を自分の回路内で再帰検証**して内包する。
  - **利点**: 渡すのは**小さな proof 1個だけ**（走行 witness は不要）。誰でも π_{i-1} を単体 verify できる
    ＝「チェーンから取ってきて検証」がそのまま成立。
  - **プライバシー**: z（集計）以外は公開しない。座標・生 RSSI は各ステップの回路内に秘匿されたまま。

**方式B（省メモリ代替・Nova）── 渡すのは「走行累積」**
- 「前の証明」の実体は **running accumulator（走行累積）= 前ステップまでを畳んだ状態**で、
  公開状態 z_{i-1} に加えて **折り畳みインスタンス U_{i-1}＋走行 witness W_{i-1}**（数十KB〜数MB級）も渡す。
  fold を「続ける」には witness も要るため。中間は単体検証不可。より厳密な秘匿には **zk-fold（ブラインド）**。
  → 「取ってきて検証」の像とはズレるため、**本設計では A を優先し B は温存**。

### 5.2 どの経路で渡すか（transport）＝ プライベート（許可型）ブロックチェーン

**共有はプライベートブロックチェーンに載せる**。各ノードは「前の累積(証明)をチェーンから取得 → 検証 →
自分を畳んで新しい累積をチェーンに書き戻す」を繰り返す。既存の許可型チェーン（`contracts/besu-qbft`,
QBFT 合意）をそのまま使う。

```
ノードi : チェーンから最新の累積 acc_{i-1} を取得
        → 自分の fold 回路で acc_{i-1} を検証(内包) + 自分の観測を折り込む
        → 新しい累積 acc_i をチェーンに書き込む（トランザクション）
ノードi+1: チェーンから acc_i を取得 … 以下同様
```

- **チェーンが担うこと**: 永続化・順序付け・可用性・全ノードへの同報（BFT 合意で全複製が同じ状態を持つ）。
  → 「取ってこられない/順序が曖昧」を避けられる。**特権ノードなしで共有基盤になる**。
- **保存形式（サイズ対策）**:
  - **方式A**: 渡すのは **z_{i-1}＋標準証明 π_{i-1}（小さい）** なので、そのまま**オンチェーンに載せられる**。
    別 blob 置き場は不要。次ノードは π_{i-1} を取得して回路内で再帰検証する。
  - **方式B**: 走行 witness は大きい（数十KB〜MB）ので、オンチェーンには **z ＋ 走行累積のハッシュ＋取得先**
    を記録し、本体（U, W）はチェーンのストレージ or 併設 blob 置き場に置いてハッシュで結ぶ。
  - 許可型チェーンなら容量に余裕を持たせやすい（パブリックのガス制約が無い）。
- **検証つき書き込み（任意）**: コントラクトが「新 acc は旧 acc を正しく1ステップ進めたもの」を
  **その場で検証**してから受理する設計にもできる（最終圧縮 SNARK をトランザクションで verify）。
  → 不正な累積はそもそもチェーンに載らない。

### 5.3 なぜ相手を信頼しなくてよいか
- 受け取った (z_{i-1}, π_{i-1})〔方式B は U_{i-1}〕を**自分の回路の中で再帰検証**する。改ざん/捏造された累積は
  **次の証明生成で成立しない**（＝弾かれる）。だから**渡してくる相手・経路を信頼する必要はない**。
- 信頼が要るのは「渡してくれるか（可用性）」だけで、正しさ（完全性・健全性）は暗号が担保。

### 5.4 順序・発見・重複（実務）
- **発見/順序**: **チェーンが持つ最新の累積**を取得すればよい（順序はチェーンが確定）。
  同時書き込みが競合しても、チェーンの合意で1本に確定（＋可換 fold なら後から合流も可）。
- **二重計上防止**: included_acc に自分が未包含のときだけ畳む（回路内で強制）。
- **可換 fold**: 順不同で同じ結果になる畳み込みにできれば、並行して伸びた累積を**後から1本に合流**できる
  → 競合・途切れ耐性が上がる（PoC で確認）。

### 5.5 残る問題＝検閲/途切れ
- 許可型チェーン（BFT 合意＋全複製）なので、**共有基盤としての「取ってこられない」問題は小さい**
  （参加ノードは同じ状態を持つ）。
- 残るのは「あるノードが自分の観測を**書き込まない/されない**」＝間引き。
  緩和: 網羅性(#3b の提出集合コミット)で間引きを検知／複数累積を並行させ合流／タイムアウト運用。

## 6. 誰が畳むか（計算の置き場）── 全ノード同等・ただし重い再帰はPi寄り

- **ラズパイもユーザ端末も同等の「ノード」**。役割の区別はなく、原理的にはどのノードも
  「観測 ＋ 前の証明を内包して自分のステップを進める」を行える（完全分散・対等）。
- **方式A（主軸）の現実的な役割分担**: 方式A の再帰検証は**1ステップが重い**（検証器を回路内で実行）。
  そのため実運用では:
  - **ラズパイ = 再帰ステップの担い手**。arm64 で gnark 再帰をネイティブ実行（計算力に余裕）。
    「前の証明を検証して内包する」重いステップはここが担う。
  - **スマホ = 末端の witness 証明だけ**。軽い circom/Groth16(rapidsnark, 実装済) で自分の観測証明を出し、
    それを近傍のラズパイが再帰チェーンに取り込む。**スマホに重い再帰は載せない**。
- **方式B（Nova）を採る場合**のみ、省メモリゆえ**スマホ自身が折り畳む**構成も検討可（端末実測は PoC 要確認）。
- コーディネータや特権ノードは置かない（対等）。「誰が重い再帰を担うか」は**能力ベースの分担**であって階層ではない。

## 7. 精度が上がるとは（なぜ多いほど良いか）

- week18 の評価: 相異なる登録端末の整合数 N が増えるほど検知率(TPR)が上がる（√N の効果）。
- チェーンが長い＝多くの**独立 witness を内包** → `consistent_count`/`suspicious_count` が確信度を表す。
- 最終判定: `consistent_count ≥ K → trusted` / `suspicious_count ≥ K → spoofAlert`。
- 「1人の主観」から「K 人の合意」へ。参加者が増えるほど閾値 K に達しやすく、確信度が上がる。

## 8. 最終圧縮とオンチェーン着地

- **方式A(gnark)**: 各 π_k がすでに BN254 Groth16 なので、最終 π_N を**そのまま EVM verifier で1回検証**できる
  （追加の wrap 不要）。中間圧縮も不要。
- **方式B(Nova)**: folded 証明は最後に**1つの簡潔な SNARK（Groth16/Spartan 等）へ圧縮（wrap）**してから着地。
- ブロックチェーンは**最終証明を1回検証**し、`(drone_id_commitment, time_bucket, consistent_count,
  suspicious_count, included_root)` を確認して trusted / spoofAlert を記録。
- ＝ オンチェーン検証は**参加者数によらず定数**。

## 9. フレームワーク（方式A主軸で確定）

| 候補 | 位置づけ |
|---|---|
| **gnark 再帰（方式A・本命）** | 現行 M2(`aggregator/`)で使用中。BN254・EVM 着地・各累積が単体検証可能＝「取ってきて検証」に忠実。逐次チェーンにも適用（重いステップは Pi が担う） |
| Nova / HyperNova / Sonobe（方式B・省メモリ代替） | 省メモリで**エッジ折り畳み**向き。ただし中間が単体検証不可。「各ノードを極力軽く」したい場合の代替 |
| Plonky2 / Halo2（方式A・別実装） | 再帰は速い/本番実績あり。ただし Plonky2 は体(Goldilocks)が現行 EdDSA(BN254)と不一致で高コスト、Halo2 は回路実装が重い |

→ **本設計の中心は gnark 再帰（方式A）**。ラズパイが再帰ステップを担い、スマホは軽い witness 証明を供給。
Nova(Sonobe) は「エッジで軽くしたくなったら」の省メモリ代替として温存し、**PoC で A と実測比較**する。

## 10. 設計上の論点（実装前に詰める決定）

1. **トポロジ**: 純チェーン(IVC) / 木(並列) / ハイブリッド（局所チェーン→木でまとめる）。
   - 純チェーンは「内包」に忠実だが途切れに弱い。ハイブリッドが堅牢性と内包の折衷。
2. **折り畳みの置き場**: 各参加者 / ラズパイ / 巡回コーディネータ。
3. **二重計上防止**: included_acc を Merkle 根にするか、ハッシュ集合にするか。
4. **順序**: 参加順は任意（可換）でよいか（可換なら並列合流もできる）。
5. **検閲/途切れ対策**: 網羅性(#3b) or 木への切替 or タイムアウト運用。
6. **端末で Nova が回るか**: スマホでの folding 実測（重ければラズパイ集約に寄せる）。
7. **最終圧縮の証明系**: EVM 着地のための wrap（Groth16 等）。

## 11. 現行 M2 との関係

- 現行 M2 = **gnark の木再帰（サーバ・N個一括検証）**。すでに実装/計測済み。
- 本設計 = **同じ gnark 再帰（方式A）を「逐次チェーン(IVC)」に組み替えたもの**。各ノードが前の証明を
  内包しながら一列に積み上げる。フレームワークは M2 と同じ gnark なので**資産をそのまま延長**できる。
- 位置づけ: M2（木・一括）と本設計（チェーン・逐次内包）は**同じ gnark 上のトポロジ違い**。
  「前を内包」に忠実なのはチェーン側。まず PoC で両トポロジを比較。

## 12. 実装前の最小 PoC 案

1. Nova/Sonobe で **2ステップの折り畳み**を回す（step 回路 = consistent_count を +ok するだけ）。
2. step 回路に **drone_id/time_bucket 一致チェック**を追加。
3. **RSSI 整合**（相対帯）を step に折り込む。
4. **membership + distinctness**（Sybil・二重計上）を追加。
5. **最終圧縮 → EVM verifier** を出力し、オンチェーン1回検証を確認。

→ まず 1〜2 で「Folding が回る・前を内包できる」ことを実証し、その後に検知ロジックを載せる。

## 13. 採用する構成（確定）── 各ノードが再帰検証する純チェーン(IVC)・方式A(gnark)

- **トポロジ = チェーン（IVC）**: 参加ノードが一列に、**前のノードの証明を内包しながら**自分の観測を足す。
- **方式 = A（再帰検証・gnark）**: 各ノードは前の累積の証明 π_{i-1} を**回路内で再帰検証**して内包し、
  自分の観測を加えた新しい累積 acc_i（＝単体検証可能な標準証明 π_i）を作る。
- **全ノード同等・ただし重い再帰は能力ベースで Pi 寄り**: ラズパイもユーザ端末も区別ない「ノード」だが、
  方式A の再帰は重いので**ラズパイが再帰ステップを担い、スマホは軽い witness 証明だけ**を供給する（§6）。
  特権ノードやコーディネータは置かない（対等）。

```
スマホ: 軽い witness 証明(circom/Groth16) ─┐
ノード1(Pi): 観測 → 再帰 → acc1(π1) ─▶ ノード2(Pi): π1を回路内検証(内包)+観測 → acc2(π2) ─▶ …
   … ─▶ ノードN: π_{N-1}を検証(内包)+観測 → acc_N(π_N) ─▶ 最終圧縮 → EVM 1回検証
   各 π_k は単体で検証可能（チェーンから取ってきて verify できる）
```

- **前提（この構成の性質）**:
  - 方式A なので**各 acc_k(π_k) が単体で検証可能**。許可型チェーンに置いて「取得→verify」が成立。
  - 重さ: 再帰検証は1ステップが重いが、**ラズパイの計算力で吸収**（スマホには載せない）。
  - **弱点＝途切れ/検閲**: 一列なので途中のノードが渡さないと止まる。→ タイムアウトで飛ばして次へ、
    複数チェーンを並走させて後で束ねる、網羅性(#3b)、等で緩和（論点として PoC 後に対処）。
  - 順序: 順不同で同じ結果になる集計にできると、渡し損ねた相手を後から合流できて堅牢。

- **省メモリ代替(方式B/Nova)**: 「スマホ自身に折り畳ませたい／連鎖が非常に長い」場合に温存。PoC で A と比較。
- 残りの論点（二重計上方式・順序の可換性・検閲対策・最終圧縮の証明系）は PoC 段で確定。

### 次アクション（PoC・方式A/gnark）
- **Step A**: gnark で「各ノードが順に前の証明を再帰検証して足す2〜3ステップ」を回し、**前を内包**できることを実証
  （step 回路 = 前の π を検証＋drone_id/time_bucket 一致チェック＋consistent_count を +ok）。
  現行 `aggregator/`（gnark・snarkimport・recursion）を土台に流用する。
- **Step B**: RSSI 整合を step に折り込む → **Step C**: membership＋二重計上 → **Step D**: 最終圧縮＋EVM 着地。

## 14. 設計の不足部分レビュー（2つの目的に照らして）

目的: **① 複数ノードで RSSI を検証** ／ **② 危険か否かを内包して証明**。この観点で足りない点。

### 充足している点
- 複数ノードの逐次内包（IVC チェーン）、同一ドローン/時間窓の束縛、consistent/suspicious の集計、
  二重計上防止、許可型チェーンでの共有、最終圧縮→オンチェーン着地。＝**骨格は揃っている**。

### 不足・要追加（優先度順）

1. **【目的②の核】危険判定を「回路内で内包」して証明する**
   - 現状はカウント(consistent/suspicious)を出し、危険/安全の結論は**契約側の判断**に委ねている。
   - 目的②「危険か否かを内包して証明」には、**最終ステップの回路内で判定まで計算し、
     `is_spoof / is_safe` を証明の公開出力にする**べき。
   - 判定規則を**一意**に（例: `suspicious ≥ K → 危険` / それ以外で `consistent ≥ K → 安全` /
     どちらも未達 → `undetermined`）。＝結論が順序や解釈に依存しない。

2. **【目的①の核】入力の真正性(R3)がステップ回路に未組込**
   - 現 §3 の step は membership と RSSI 整合のみ。**「そのノードが本物のドローン放送を受けた」保証が無い**。
   - 各ステップで **ドローン署名の検証・freshness(鮮度)・観測とその放送の束縛**を折り込む必要。
   - でないと、ノードが**捏造した RSSI/放送で“整合”を作れて**しまい、複数ノード検証の意味が崩れる。

3. **端末 GPS の真正性と「空間的多様性」**
   - RSSI 整合は各ノードの GPS に依存。**GPS を偽れば偽の整合**を作れる → 端末アテステーションで束縛。
   - 複数ノード検証の価値は**ノードが異なる場所にいる**こと。同一地点の結託を避けるには
     **位置の分散**を担保したい（device の distinct だけでは不十分な場合がある）。

4. **RSSI 較正の一貫性・物理妥当性（ZKP の外の限界）**
   - 検知は A/n/σ 較正に強く依存（未較正だと検知率が崩壊）。**ZKP は「計算が正しい」ことは証明するが、
     入れた較正値が物理的に妥当かは証明しない**。
   - 各ノードがバラバラの較正を使うと結論の意味が薄れる → **較正プロファイルを証明にバインド**し、
     監査可能にする（or 環境別プロファイルの合意）。＝設計に明示すべき限界と対処。

5. **リプレイ/鮮度**
   - 古い累積や古い放送の**再提出(リプレイ)**を防ぐ nonce/時刻束縛が要る（time_bucket だけでは不足な場合）。

6. **可換 fold / 二重計上の確定**
   - 順不同で同結果になる畳み込み（合流可能）と included_acc の方式は、設計に挙げたが**PoC で確定**が必要。

7. **走行 witness のプライバシー**
   - ノード間で渡す走行累積が各ステップの秘密を露出しないよう **zk-fold（ブラインド）**の要否を確認。

### まとめ（この2目的のために最低限足すべき3点）
- **(a) 危険判定を回路内で計算し `is_spoof` を証明出力に**（目的②を“内包”で満たす核）。
- **(b) 各ステップに入力真正性(ドローン署名・freshness・放送束縛)を組込む**（目的①を成立させる核）。
- **(c) GPS 真正性＋較正の扱いを設計に明示**（多ノード検証が意味を持つ前提）。

→ (a)(b) は step 回路の必須拡張、(c) は前提条件（アテステーション・較正運用）。残りは PoC で確定。
