# ZKP 設計 ── 何を証明したいのか（目的と要件）

作成日: 2026-07-23 / 目的: フレームワーク選定の前に、「この研究で ZKP を使って**何を証明し、何を隠し、
どんな性質が要るか**」を design として固める。関連: week18 検知設計 / week19 回路・比較 / week20 可否。

---

## 0. 一言で

**「周囲の端末が受けた電波(RSSI)から、放送された位置が物理的に矛盾しないか」を、
端末の座標や生 RSSI を明かさずに証明し、複数端末の証明を1つにまとめて「なりすまし合意」を作る。**

ZKP を使う理由は2つ:
1. **プライバシー**: 通りすがりの端末の正確な位置・生 RSSI を晒さずに検証したい。
2. **ごまかせなさ(健全性)**: 「整合した/矛盾した」という判定を、端末が嘘をつけない形で確定したい。

---

## 1. 誰が何を証明するのか（ステートメント）

### 1端末（witness）が証明する主張
> 「私は**登録された観測端末**で、あるドローン放送（ID・放送位置 P_claim・時刻 t）を受信した。
> 私の GPS 位置から P_claim までの**幾何距離 d_claim** と、RSSI から推定した**実測距離 d_meas** が、
> 相対許容帯（±r）で**整合する（または矛盾する）**。ただし**自分の座標と生 RSSI は明かさない**。」

これを回路で計算・強制し、**結果(consistency_ok = 1/0)だけ**を公開する。

### N 端末をまとめて証明する主張（集約）
> 「**相異なる登録端末** N 台が、**同一ドローン・同一時間窓**の放送について各自判定し、
> そのうち K 台以上が整合（または矛盾）した。」

→ これで「1台の主観」ではなく「**分散した複数端末の合意**」になる。

---

## 2. 隠すこと / 公開すること

| | 内容 | 理由 |
|---|---|---|
| **隠す（秘匿）** | 端末の正確な GPS 座標、生 RSSI サンプル | 通行人端末のプライバシー・生データ独占の回避 |
| **公開（検証に必要）** | consistency_ok（整合1/矛盾0） | 合意カウントの材料 |
| 公開 | drone_id のコミットメント | 「どの放送か」を束ねる（IDそのものは隠せる） |
| 公開 | time_bucket（時間窓） | 「同じ瞬間の放送か」を束ねる |
| 公開 | 端末が登録集合のメンバーである事実 | Sybil 対策（どの端末かは Merkle で隠す） |

**設計原則**: 公開するのは「合意を数えるのに必要な最小限」だけ。位置・生データは回路の外に出さない。

---

## 3. 必要な性質（ZKP への要件）

| # | 要件 | 何のため | 効いてくる選択 |
|---|---|---|---|
| R1 | **ゼロ知識（秘匿）** | 座標・生RSSIを隠す | 全 ZKP 共通で満たす |
| R2 | **健全性（ごまかせない）** | 判定を偽れない | 全 ZKP 共通で満たす |
| R3 | **入力の真正性に束縛** | 偽端末・偽入力・再利用を防ぐ | 回路内で端末署名・ドローン署名・freshness を検証（★2） |
| R4 | **集約できる** | 多端末を1つに（K-of-N） | 再帰(gnark) or Folding、または回路内バッチ |
| R5 | **オンチェーンで安く検証** | 合意をチェーンに記録 | Groth16 が最安（gas）／証明系選択に直結 |
| R6 | **スマホで証明生成できる** | 各端末がオンデバイスで作る | prover が arm64・軽量（→ week20 可否） |
| R7 | **健全なセットアップ** | 鍵の儀式で偽造されない | 正規セレモニー(★1) or セットアップ不要な証明系 |

→ **R5・R6・R7 が、どのフレームワークを選ぶかを実質決める**（R1・R2 は皆満たす）。

---

## 4. 非目標（やらないこと・原理的限界）

- **放送位置が“真である”ことの証明ではない**。あくまで「物理と**矛盾しない/する**」の検知。
- **中継/ワームホール攻撃の防御はしない**（RSSI 単独では原理的に不可・distance-bounding が要る）。
- **ドローン側の改造はしない**（受信側だけで完結）。
- ジャミング等の可用性攻撃は対象外。

---

## 5. いま実装されている形（設計の現状）

- **1端末回路**: `remoteid_consistency_rel.circom`（R1・R2 の核＝整合を秘匿証明。~650制約）
  および `uav_witness_attestation.circom`（＋R3: 端末/ドローン署名・freshness・commitments。~11.8k制約）。
- **集約(R4)**: `aggregator/`（gnark 再帰）＋ membership(#3a)・completeness(#3b)。
- **オンチェーン(R5)**: `AttestationRegistry`（Groth16 検証・K-of-N 集計）。
- **スマホ(R6)**: アプリで circom/Groth16 を rapidsnark で証明（RSSI 整合回路を選択式で追加済）。
- **セットアップ(R7)**: 正規セレモニー実装済（★1）。

---

## 6. これがフレームワーク選定にどう繋がるか

「何をしたいか(R1〜R7)」を**制約**に翻訳すると、選択が絞れる:

- R5（安いオンチェーン検証）を重視 → **Groth16（circom）が最有力**。
- R7（セットアップ健全性を構造で消したい）→ **Noir/STARK/Folding**（ただし R5 の gas 増とトレードオフ）。
- R4（集約）を端末側で軽く → **Folding(Nova)**。サーバ側で確実に → **gnark 再帰**。
- R6（スマホ証明）→ **circom/rapidsnark（実証済）** が本命、Noir は条件付き（Android は Zig）。

→ **結論の順序**: まず R1〜R7（本書）で「何を・どんな性質で証明するか」を固定し、
その後に week19/05（決定）・week20（スマホ可否）で「乗り物(フレームワーク)」を選ぶ。

---

## 7. 一枚まとめ

```
証明したいこと : 「登録端末が、同一ドローン放送について、座標を隠したまま
                  RSSI 整合(整合/矛盾)を判定し、K台で合意した」
隠すこと       : 端末の座標・生RSSI
公開すること   : 整合結果 / drone_id・time_bucket のコミット / 登録メンバーである事実
要件           : 秘匿・健全・入力真正性・集約・安いオンチェーン検証・スマホ生成・健全な鍵
非目標         : 位置の真正性証明・中継対策・ドローン改造
```
