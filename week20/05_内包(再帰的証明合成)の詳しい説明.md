# 「内包」＝再帰的証明合成の詳しい説明

作成日: 2026-07-23 / 目的: 「他の証明結果に自分の証明を入れて検証する（＝内包）」が、暗号的に何を意味し、
どう動き、どんな実現方式があるかを**やさしく詳しく**説明する。関連: week20/04（再帰ZKP設計）。

---

## 1. まず「証明」とは（前提）

ゼロ知識証明(proof) = **「ある主張が正しい」ことを、中身を見せずに示す短いデータ**。
- 例（本案件の1ノード）: 主張 =「私は登録端末で、RSSI と放送位置が整合する（consistency_ok=1）」。
- 検証者は proof を**検証(verify)**するだけで、主張が正しいと確信できる（計算をやり直さなくてよい）。

ポイント: **検証はとても軽い**。だから「証明を、別の計算の“部品”として使い回す」ことができる。
これが次の「内包」の土台。

---

## 2. 「内包」とは何か（コンセプト）

**内包 = 他人の証明を、自分の証明の“中で検証”して、両方まとめて1つの新しい証明にすること。**

あなたのイメージ通り「**他の証明結果に自分の証明を入れて検証する**」です。暗号では
**再帰的証明合成（recursive proof composition）／ IVC（逐次的検証可能計算）** と呼びます。

```
    ┌─────────────────────────────────────────────┐
    │ 私の証明(proof_i) が主張すること:            │
    │   「① 前の人の証明(proof_{i-1}) は正しい     │  ← 前を“中で検証”
    │     ② かつ 私の観測(RSSI整合)も正しい」      │  ← 自分を足す
    └─────────────────────────────────────────────┘
```

- 私の回路(circuit)は、**前の proof を検証する処理そのものを内部に持つ**。
- 私が proof を作ると、それは「前の proof が有効 **かつ** 私のステップも有効」を一度に保証する。
- これを繰り返すと、**入れ子(nesting)** になる:

```
proof_1
proof_2 = 「proof_1 は正しい」＋「ノード2の観測」
proof_3 = 「proof_2 は正しい」＋「ノード3の観測」
   …
proof_N = 「proof_{N-1} は正しい」＋「ノードNの観測」
```

→ **最後の proof_N を1回検証するだけで、1〜N の全部が正しいと分かる**（伝播して保証される）。
これが「多数のノードの検証を1つにまとめる」正体。

---

## 3. なぜ「相手を信頼しなくてよい」のか

- 私は前の proof を**自分の回路の中で検証**する。もし前の proof が**偽物・改ざん**なら、
  私の証明生成は**成立しない**（数学的に作れない）。
- だから「前の人が正直か」を信じる必要がない。**信じるのは数学（検証が通ったという事実）だけ**。
- ＝「他人の結果を鵜呑みにする」のではなく「**他人の結果を検証してから取り込む**」。ここが内包の肝。

---

## 4. 具体的な流れ（本案件・チェーン＋プライベートチェーン共有）

```
ノードi の手順:
 1. プライベートチェーンから「前の証明 proof_{i-1} と累積状態 z_{i-1}」を取得
 2. 自分の回路の中で proof_{i-1} を検証（＝内包・取り込み）
 3. 同じドローン・同じ時間窓か確認し、自分の RSSI 整合(consistent/suspicious)を計算
 4. カウントを更新した新しい累積 z_i を作り、新しい証明 proof_i を生成
 5. proof_i と z_i をチェーンに書き戻す（次のノードが取得できる）
```

- z（累積状態）が持つもの: drone_id / time_bucket / consistent_count / suspicious_count /
  参加済ノード集合 / step。**座標や生 RSSI は入れない（秘匿）**。
- 参加ノードが増えるほど count が育ち、**危険/安全の確信度が上がる**。

---

## 5. 「内包」の実現方式は2つある（重要）

同じ「内包」でも、**前の証明をいつ検証するか**で2通りある。

### 方式A ── 再帰検証（各ステップで“その場で”検証）
- 各ノードの回路が**前の証明の検証器(verifier)を丸ごと内部で実行**する。
- **各ステップの proof が、それ単体で完全に検証可能**（誰でも取ってきて verify できる）。
- 「他の証明を**入れて検証**する」「チェーンから**取ってきて検証**できる」に**最も忠実**。
- 代償: 検証器を回路内で回すので**1ステップが重い**。
- 代表: **gnark 再帰（現行 M2 で使用中）／ Plonky2 ／ Halo2**。

### 方式B ── Folding（畳み込み・検証は最後に1回だけ）
- 各ステップでは前の証明を**「畳み込む」だけ**（完全な検証は保留）。最後に**1回だけ**まとめて検証。
- **1ステップがとても軽い・省メモリ**。長い連鎖に強い。
- 代償: **中間の“証明”は単体では検証できない**（最後に圧縮するまで verify 不可）。
  →「チェーンから取ってきて検証」の像とはズレる。
- 代表: **Nova ／ HyperNova ／ Sonobe**。

### 比較表
| | A. 再帰検証 | B. Folding |
|---|---|---|
| 前の証明を | その場で完全検証 | 畳み込む（検証は最後） |
| 中間の証明 | **単体で検証可能** | 単体では検証不可 |
| 1ステップの重さ | 重い | 軽い・省メモリ |
| 「取ってきて検証」 | ○ どの累積も検証可 | △ 最終圧縮まで不可 |
| 代表 | gnark / Plonky2 / Halo2 | Nova / Sonobe |

---

## 6. 本案件はどちらか

あなたの2つの説明 ──「**入れて“検証”する**」「**チェーンから取ってきて検証**」── は、
**両方とも方式A（再帰検証）**を指している。

- 各ノードの累積が**そのまま検証可能な証明**なので、チェーンに置いて「取ってきて verify」が成立。
- 「前の証明を自分の中で検証してから取り込む」がステップごとに実際に起きる。

→ **主軸は A（再帰検証）**。フレームワークは**再帰が素直な gnark（既に M2 で使用）**が第一候補。
B(Folding/Nova)は「各ノードを軽くしたい」場合の**省メモリな代替**として温存（ただし中間は単体検証不可）。

## 7. 図でまとめ

```
【方式A：再帰検証（各ノードが前を検証して取り込む・本案件）】

 チェーン: [proof_1] → [proof_2] → [proof_3] → … → [proof_N]
              ▲          ▲                          │
   ノード2 が proof_1 を取得→回路内で検証→自分を足す→proof_2 を書き戻す
   どの proof_k も「取ってきて単体で検証」できる。最後の proof_N が全部を保証。

【方式B：Folding（畳むだけ・最後に1回検証）】

 acc_1 ⊕ step2 → acc_2 ⊕ step3 → … → acc_N ──(最後に1回だけ)──▶ 検証
   軽いが、途中の acc は単体検証できない。
```

---

## 8. まとめ（一言で）

- **内包 = 他人の証明を自分の回路の中で検証して、自分の証明と1つにまとめること**（再帰的証明合成）。
- だから**相手を信頼せず**、検証が通った事実だけを取り込める。連鎖させると**1回の検証で全ノード分**を保証。
- 「入れて検証」「取ってきて検証」を満たすのは **方式A（再帰検証）**＝各累積が単体で検証可能。
  本案件は A を主軸、フレームワークは **gnark 再帰**が素直。Folding は省メモリの代替。
