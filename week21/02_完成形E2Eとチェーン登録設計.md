# 完成形 E2E とチェーン登録設計

作成日: 2026-09-27 / 目的: 「何をチェーンに登録しているのか」を明確にし、端末観測から最終判定までを一本の完成形として実装するための設計を定める。

関連: `00_これまでの総まとめ_目的と到達点.md`、`NEXT_STEPS.md`、`contracts/`、`aggregator/cmd/aggregate/`。

---

## 0. 結論（先に）

採用する完成形は、**個々の観測をチェーンへ逐一登録せず、登録済み端末による複数の ZK 証明を集約し、最終の集約証明と判定だけを 1 セッション 1 回チェーンに登録する方式**とする。

これにより、チェーン上で読む人は「どのドローン・どの時間窓について、何台が整合／矛盾と判定したか、どの登録端末集合に基づくか」を一件のレコードとして追える。一方、端末の正確な位置、生 RSSI、個々の証明本文は公開しない。

現状は次の二つが別経路で存在する。

- **M1**: `AttestationRegistry` に端末証明を 1 件ずつ直接提出する経路。E2E テスト済み。
- **M2**: `aggregator/cmd/aggregate` が 3 件を再帰集約し、`AggregateVerifier` が集約証明を検証する経路。証明検証テスト済み。

`FinalAttestationRegistry` とその状態遷移テストは実装済みである。集約回路も新しい公開値を出すよう更新した。現在の残作業は、旧3入力形式の fixture / `AggregateVerifier` を新5入力形式で再生成し、実際の aggregate proof を最終レジストリへ通すことである。

## 1. 完成形で利用者が見る流れ

```text
Remote ID 放送
   │
   ├─ 端末 A: RSSI/GPS を秘密にして leaf proof を作る ─┐
   ├─ 端末 B: RSSI/GPS を秘密にして leaf proof を作る ─┼─ [集約器]
   └─ 端末 C: RSSI/GPS を秘密にして leaf proof を作る ─┘
                                                         │
                                         同一 drone・同一時間窓・登録端末・重複なしを強制
                                                         │
                                                         ▼
                                          集約証明 π_final と公開結果 z_final
                                                         │
                                                         ▼
                                    [チェーン] 1 セッションにつき 1 件だけ Finalized
```

チェーンには、各端末の座標・RSSI・生証明を登録しない。登録するのは次だけである。

| 項目 | 意味 | 公開する理由 |
|---|---|---|
| `sessionId` | `droneIdCommitment` と `timeBucket` から作る観測セッション識別子 | 同じ放送についての記録を一意に参照するため |
| `consistentCount` | 物理観測が整合した端末数 | 裏取りの根拠を示すため |
| `suspiciousCount` | 物理観測が矛盾した端末数 | なりすまし疑いの根拠を示すため |
| `memberRoot` | 許可された端末集合の Merkle Root | Sybil 対策がどの登録集合に基づくか示すため |
| `verdict` | `Trusted` / `SpoofSuspected` / `Undetermined` | アプリや監査者が読む最終結果 |
| `proofHash` | 提出された集約証明のハッシュ | 同じ証明の重複登録を防ぎ、追跡するため |

`sessionId`、件数、`memberRoot` は**集約証明の public input / output に含める**。コントラクトは、証明を検証してから同じ値を保存する。これにより、リレーや提出者が「別のドローンの結果」として付け替えることを防ぐ。

## 2. チェーン登録の設計候補

### 案A: 個別証明をすべて直接登録（現在の M1）

```text
端末ごとの leaf proof ──► AttestationRegistry ──► K-of-N 判定
```

- 長所: 仕組みが単純。各端末の提出・拒否をチェーン上で追える。既に E2E テスト済み。
- 短所: 端末数に比例してガスとトランザクションが増える。各端末がチェーンへ到達できる必要がある。
- 向く用途: デモ、少数端末、監査で各提出を公開したい場合。

### 案B: 最終集約証明だけを登録（推奨）

```text
leaf proof 群 ──► 集約器 ──► π_final ──► FinalAttestationRegistry
```

- 長所: チェーン上の検証は 1 回で一定。端末の通信負荷と公開情報を抑えられる。
- 短所: 個々の leaf proof をどこで保持・取得するかを別途決める必要がある。
- 向く用途: 本研究の本命。複数端末・プライバシー保護・定数ガスという目的に合う。

### 案C: ハイブリッド（最終証明 + 監査用コミットメント）

```text
leaf proof 群 ──► 集約器 ──► π_final + evidenceRoot ──► FinalAttestationRegistry
                         └── proof blob / 受信ログは off-chain 保管
```

- 長所: チェーンは軽いまま、必要時に監査できる。提出集合の改ざん・間引きも検出しやすい。
- 短所: off-chain の保存先、保持期間、アクセス権を設計する必要がある。
- 向く用途: 実運用を見据える場合。**案Bをまず完成させた後に拡張する。**

## 3. 推奨する状態遷移

最終レジストリでは、1 セッションを次の状態として管理する。

```text
Open（観測受付）
  │
  └─ 集約証明を提出・検証
          │
          ├─ consistentCount >= K ─► Trusted（確定）
          ├─ suspiciousCount >= K ─► SpoofSuspected（確定）
          └─ いずれも未満 ─────────► Undetermined（暫定）
```

実装の最小版では `Open` をオンチェーンで明示的に作らず、初回の有効な `submitFinal` でセッションを作成してよい。後から複数回の更新、提出期限、異議申立てを扱う必要が出たときに `Open` / `Finalized` を明示した状態機械へ拡張する。

**重要なルール**:

1. `sessionId` は集約証明に束縛する。コントラクト引数だけで受け取らない。
2. `memberRoot` は集約証明に束縛し、オンチェーンの登録 Root と照合する。
3. `nullifierRoot` または同等の二重計上防止状態も、Step C 完了後は集約証明に束縛する。
4. 最終レコードは `proofHash` を保存し、同じ証明の再提出を拒否する。
5. `Trusted` と `SpoofSuspected` の両方が後から同一セッションに立たないよう、最終化規則を一意にする。

## 4. 大きな実装順序

細部を先に増やさず、縦に通す。

### E2E-1: 集約証明を「どの結果か」へ束縛する

`AggCircuit` の公開出力を次の形に拡張する。

```text
(droneIdCommitment, timeBucket, consistentCount, suspiciousCount, memberRoot)
```

回路はすでに各 leaf proof の `droneIdCommitment` と `timeBucket` の一致を確認している。これらを最終証明の public output として出すことで、オンチェーン記録との付け替えを防ぐ。

### E2E-2: `FinalAttestationRegistry` を追加する

集約 verifier を呼び、公開値を保存するコントラクトを作る。

```solidity
submitFinal(proof, publicInputs)
  1. AggregateVerifier.verifyProof(proof, publicInputs)
  2. memberRoot == deviceRoot を確認
  3. sessionId が未確定であることを確認
  4. verdict を counts と K から決定
  5. Finalized(sessionId, verdict, counts, memberRoot, proofHash) を emit
```

### E2E-3: 1 コマンドのデモにする

既存 fixture を使い、次を連続で見せる。

1. 3 台の leaf proof が有効である。
2. 2 整合・1 矛盾である。
3. 集約 proof が有効である。
4. final registry に 1 件の最終レコードができる。

### E2E-4: Step C を統合する

登録端末 membership と二重計上防止を集約回路へ入れ、未登録・重複端末では E2E が失敗することを確認する。

## 5. 現時点で正直に言えること

既存の `scripts/run_e2e_demo.sh` は、現行の M1 E2E テスト、M2 集約 proof 検証テスト、final registry の状態遷移テストを一つの入口から実行する。これは**完成形の部品がすべて動くことを確認する統合スモークテスト**である。

ただし、現在追跡済みの集約 proof fixture は旧3入力形式である。そのため「実 aggregate proof が検証できる」と「実 aggregate proof の結果がセッションとして保存される」は、まだ一つの処理ではない。新5入力の proof / Solidity verifier を再生成して E2E-1 / E2E-2 を接続した時点で、真の end-to-end 完成形になる。

この区別を明記したうえで進めることで、デモの見た目だけを E2E と呼んで安全性の穴を見落とすことを防ぐ。

## 6. 可視化ビューの設計 — ハッシュではなく意味を見せる

ハッシュ、proof bytes、Merkle Root は監査には必要だが、通常の利用者が判定を理解するための表示ではない。ダッシュボードの標準表示は、セッションごとに次を見せる。

1. **結果**: `Trusted` / `SpoofSuspected` / `Undetermined` と、その理由（例: 整合 2、矛盾 1、閾値 K=2）。
2. **流れ**: 観測端末 → leaf proof → 集約 → チェーン記録をノードグラフで表示する。
3. **チェーンの出来事**: block number、確定時刻、検証済みか、最終化されたかを時系列で表示する。
4. **監査情報**: `sessionId`、`memberRoot`、`proofHash` は「詳細を開く」にのみ表示し、コピー可能にする。

画面で最も大きく見せる数値はハッシュではなく、`整合数 / 矛盾数 / 必要閾値 / 最終判定` とする。秘密情報（座標・生 RSSI・端末実名）は常に非表示にする。

```text
観測 3 台  ──► 有効な ZK 証明 3 件 ──► 整合 2 : 矛盾 1 ──► Trusted
                                          K = 2              Block #1024
```

このビューは最終レジストリの `Finalized` イベントをデータ源にする。したがって E2E-2 の `FinalAttestationRegistry` を実装する際は、フロントエンドが必要な値を一度のイベント購読で取得できるイベント設計にする。
