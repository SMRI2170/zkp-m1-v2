# 方式B（Nova）── 検証漏れ問題と対処設計

作成日: 2026-07-29 / 目的: `week20/12`§4・`week20/13`で確認した「Novaのfoldは前のインスタンスの
正しさを自動チェックしない」という性質が、実際にチェーンを回したときに何を意味するかを整理し、
対処案を検討する。**設計文書であり、実装はまだ行っていない。**

前提: `week20/12`・`week20/13`で確認済みの事実をこのドキュメントの出発点とする。
- Sonobeの`prove_step`（fold）は前のインスタンスを検証せず、ただ線形結合するだけ（`week20/12`§7）
- `from_ivc_proof`自体も受け取った`IVCProof`の正当性チェックをしない（`week20/12`§4）
- 素のNovaの`IVCProof`は前ユーザの生witnessをそのまま含む（`week20/13`§3）

---

## 0. 結論（先に）

**方式A（gnark再帰検証）は「隣を検証すればチェーン全体が正しいと保証される」という性質が
暗号学的に強制されるが、方式B（Nova）は同じ性質を得るために各参加者が自主的に`verify()`を
呼ぶ必要があり、誰かがサボると①不正の混入に気づけない②最後にまとめて失敗しても③どこで
混入したか特定できない、という3段階の弱点を持つ。** 対処には、(a)検証を強制するラッパー、
(b)毎ステップPCD化（`week20/13`で既出）、(c)署名ログによる事後追跡、(d)方式Aへの部分的フォールバック、
の4方向があり、実装コストと得られる保証のバランスで選ぶ必要がある。

---

## 1. 問題の再確認

チェーンは「参加者iが参加者i-1だけを検証し、参加者i+1から検証される」という隣接ペアの繰り返しで
全体の正しさを保証する（推移性）。この構造が成立する条件は、**各参加者が実際に「直前を検証する」を
実行していること**である。

| | 方式A（gnark再帰検証） | 方式B（Nova, 明示verify省略時） |
|---|---|---|
| 「前を検証する」は何によって強制されるか | 回路の制約そのもの（Groth16検証式を回路内で評価） | 何によっても強制されない（`prove_step`はチェックしない） |
| 不正な前状態を渡された場合 | 次の証明が生成できない（即座に失敗） | 何も起きず先に進める |
| 不正の発覚タイミング | 生成時点（該当ステップで） | チェーン全体の最後、`verify()`を呼んだ時 |
| 不正の混入箇所の特定 | 自動的に分かる（発覚した場所＝混入箇所） | 分からない（N人の誰かとしか言えない） |
| 「隣だけ検証すればよい」という前提の成立 | 常に成立 | **各参加者の善意（verify呼び出し）に依存** |

これは`week20/12`の「§12 非信頼リレー」の前提（中継ノードは暗号を偽造できないので信頼不要）にも
影響する。方式Bでは中継ノードだけでなく**参加者自身の律儀さ**への依存が新たに発生する。

---

## 2. 対処案

### 2.1 検証を強制するラッパー（実装コスト: 低）

`ChainState`（`nova_poc/nova-mobile/src/lib.rs`）に、外部から受け取った`IVCProof`を
`from_ivc_proof`する前に**必ず`N::verify()`を呼ぶ**ラッパー関数を用意し、生の`from_ivc_proof`を
直接呼べないようにAPI設計で強制する。

```rust
// 案: ChainStateに新設するコンストラクタ
pub fn resume_from(ivc_proof: IVCProof, ...) -> Result<Arc<Self>, NovaMobileError> {
    N::verify(vp.clone(), ivc_proof.clone())?;   // まずここで前状態を検証。失敗すれば即エラー
    let fs = N::from_ivc_proof(ivc_proof, (), params)?;
    Ok(Arc::new(Self { inner: Mutex::new(fs) }))
}
```

- **利点**: 実装コストが低い。ライブラリの既存機能（`N::verify`）をそのまま使う。
- **限界**: これは「アプリのAPI設計」による強制であり、暗号学的な強制ではない。悪意ある参加者が
  このラッパーを経由しない独自実装（生の`from_ivc_proof`を直接呼ぶ改造クライアント）を使えば
  依然として回避できる。**方式Aのような"回避不可能"な保証にはならない。**
- 混入箇所の特定については改善する: 「受け取った時点でverifyする」ため、**不正の発覚が
  最後ではなく受け取った参加者の手元で起きる**ようになり、「自分より前に問題がある」ことは
  即座に分かる（ただし「前の誰が原因か」は依然としてこのラッパーだけでは分からない）。

### 2.2 毎ステップPCD化（`week20/13`§4で既出、実装コスト: 高・未計測）

Sonobeの`Decider`（`folding-schemes/src/folding/nova/decider.rs`）を毎ステップ使い、
畳み込んだIVC状態を都度小さいSNARKへ圧縮してから次の参加者に渡す。こうすると:

- 次の参加者が受け取るのは「圧縮された証明」であり、これ自体が独立検証可能（方式Aのπ_iと同じ性質）。
- **不正な前状態からは、そもそも有効な圧縮証明が作れない**ため、方式Aと同じ「検証は強制される」
  性質を取り戻せる。§2.1の「API設計による強制」より強い、暗号学的な強制になる。
- **コスト**: Deciderは本来「最後に1回」使う想定の重い処理（Groth16証明生成）。毎ステップ実行すると
  `week20/08`で確認した方式Bの速度優位性（方式Aの30〜50倍）が目減りする可能性が高い。
  **具体的にどの程度かは未計測**（`week20/13`§4.1で指摘済みの最重要な検証項目）。

### 2.3 署名付きログによる事後追跡（実装コスト: 中）

各参加者が「自分が受け取った`IVCProof`のハッシュ」と「自分が新しく生成した`IVCProof`のハッシュ」を
自分の秘密鍵で署名し、非信頼リレー／許可型チェーンに記録しておく。

- §2.1・2.2のような**事前の防止**ではなく、**事後の説明責任（accountability）**を提供する対処。
- 最終`verify()`が失敗した場合、ログを遡ることで「どの参加者が、どの`IVCProof`を受け取って、
  どの`IVCProof`を渡したか」の記録が残っているため、**疑わしい参加者を絞り込める**
  （完全な暗号学的特定ではないが、運用上の説明責任は果たせる）。
- 既に提案されている§9のnullifier・§10のMerkleメンバーシップと組み合わせれば、
  「どの登録端末が関与したか」まで匿名性を保ったまま追跡可能な設計にできる余地がある（要検討）。

### 2.4 方式Aへの部分的フォールバック（実装コスト: 設計判断のみ）

「検証の強制力」が特に重要な場面（例: 最終的にオンチェーンへ記録する直前のステップ、あるいは
K-of-N判定が確定する境界のステップ）だけ方式A（gnark再帰検証）を使い、それ以外の中間ステップは
方式Bで高速に処理する、というハイブリッド構成。

- `week20/04`が元々「方式Aが主軸・方式Bは省メモリ代替」としていた位置づけに近い発想を、
  「ステップ単位で使い分ける」形に発展させたもの。
- 実装コストは新規のクリプト設計ではなく、既存の`aggregator/cmd/chainpoc`（方式A）と
  `nova_poc/nova-mobile`（方式B）を**どのステップで切り替えるか**という運用設計の問題になる。

## 3. 対処案の比較

| 案 | 防止/事後 | 強制力 | 実装コスト | 性能への影響 |
|---|---|---|---|---|
| 2.1 verify強制ラッパー | 事前（アプリ層） | API設計による強制（回避可能） | 低 | ほぼ無し（verify自体は軽い） |
| 2.2 毎ステップPCD化 | 事前（暗号学的） | 強い（方式Aと同水準） | 高 | 大（未計測、速度優位性が目減りする可能性） |
| 2.3 署名ログ | 事後 | 説明責任のみ（防止しない） | 中 | ほぼ無し |
| 2.4 方式Aフォールバック | 事前（重要ステップのみ） | 強い（方式Aと同水準、部分適用） | 設計判断のみ | 該当ステップのみ増加 |

## 4. 推奨する次の一手

1. **まず2.1（verify強制ラッパー）を実装する**: コストが最も低く、「アプリを正しく使えば方式Aと
   同じ推移性が得られる」状態を最短で作れる。`week20/13`で提案した第2段階（独立証明＋集約）とは
   独立に進められる。
2. **2.2のコストを1ステップだけ計測する**: `week20/13`§4.1・§6で既に次の一手として挙げていた
   実験（`Decider::prove`を1回呼んで時間・サイズを測る）を先に行い、「毎ステップPCD化が現実的か」を
   判断してから2.2に着手するか決める。
3. 2.3（署名ログ）は§9のnullifier・§10のMerkleメンバーシップ（`Step C`相当、まだ⬜未着手）と
   合わせて設計するのが効率的なので、そちらの実装時に一緒に検討する。
4. 2.4は新規実装ではなく運用設計の議論なので、2.1・2.2の実測結果が揃ってから、
   「どのステップにどの方式を使うか」を決める。
