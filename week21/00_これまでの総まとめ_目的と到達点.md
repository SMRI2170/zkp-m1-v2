## 0. 結論（先に）

本研究のゴールは、**ドローンが Remote ID で名乗る位置が物理的にもっともらしいかを、周囲の複数端末が位置・生 RSSI を公開せずに確かめ、なりすましの疑い／裏取り成立を検証可能な形で残すこと**である。

当初は「スマホとドローンが近いことを示す」単発の ZK 証明だった。そこから、RSSI を使う物理的な矛盾検知、複数端末による K-of-N 合意、入力真正性、再帰的な証明集約へと広げてきた。

**現在の到達点は、再帰チェーンの Step A/B まで完了。次は Step C（登録端末の確認と二重計上防止）の実装である。**

---

## 1. なぜこの研究をするのか

Remote ID は、ドローンが自分の ID や位置を周囲へ放送する仕組みである。しかし、受信側だけでは、その位置が本当に正しいかを直接は判断できない。

そこで、周囲の端末を witness（観測者）として使う。各端末は次の二つの距離を比較できる。

- **申告距離**: ドローンが放送した位置と、自端末の GPS 位置から計算する距離
- **実測距離**: 受信した電波強度（RSSI）から推定する距離

本当にその位置から放送していれば両者は概ね整合する。位置を大きく偽れば、両者が乖離しやすい。ただし端末の位置や生の RSSI は個人情報・行動情報になり得るため、公開して集める方式にはしたくない。

そのため、各端末は「整合した／矛盾した」という判定だけをゼロ知識証明で示し、複数端末の結果だけを集約する方針にした。

## 2. 最終的に作りたい全体像

```text
ドローンの Remote ID 放送
        │
        ▼
[各端末] RSSI と GPS で物理的整合を判定
        │  座標・生 RSSI は秘密のまま ZK 証明
        ▼
[集約] 同一ドローン・同一時間窓について、複数の登録端末の結果を合算
        │  K 台以上の整合／矛盾を判定
        ▼
[記録] trusted / spoof suspected を検証可能な形で記録
```

この構成で守りたい性質は次の通り。

| 守りたいこと | 必要になる仕組み |
|---|---|
| 端末の位置・生 RSSI を見せない | ゼロ知識証明 |
| 1 台の誤判定に依存しない | 複数 witness の K-of-N 合意 |
| 同じ端末の水増しを防ぐ | 登録端末確認・nullifier・二重計上防止 |
| 古い観測の使い回しを防ぐ | freshness と署名 |
| 集約結果を後から改ざんできない | 検証可能な集約証明・チェーン記録 |

なお、この仕組みが示すのは「較正済みの RSSI モデルと真正な観測を前提に、放送位置と物理観測が整合するか」である。RSSI 単独で中継／ワームホール攻撃を完全に防いだり、ドローンの絶対的な真位置を証明したりするものではない。

## 4. 現在できていること

### 4.1 端末での観測と単発証明

- BLE/Wi-Fi Remote ID を受信し、スマホの GPS・センサー情報と組み合わせられる。
- RSSI の複数サンプルを中央値で集約し、相対許容帯で整合を判定する。
- Circom/Groth16 により、位置・生 RSSI を公開せずに判定を証明できる。
- Circom、Noir、Nova は実機 Android での証明生成・検証まで検証記録がある。

### 4.2 複数端末の合意

- M1 は各端末の証明を検証し、同一ドローン・同一時間窓について K-of-N を数える。
- 整合票が閾値に達すれば `trusted`、矛盾票が閾値に達すれば `spoofAlert` として扱う。
- 署名・freshness・登録オペレータ・登録端末を扱うための回路／コントラクト資産がある。

### 4.3 再帰集約の PoC

- 方式A（gnark）は、前の証明を回路内で検証して次の証明へ内包する 3 ステップ連鎖を実装済み。
- RSSI の `ok` を外部入力で自己申告できないよう、回路内で算出する Step B も実装済み。
- 方式B（Nova）は同じ状態遷移を高速・省メモリに処理できる PoC を実装済み。ただし中間証明の独立検証と端末間の安全な引継ぎは未解決である。

## 5. まだ完了していないこと

### 最優先: Step C — Sybil と二重計上の防止

再帰チェーンに次を統合する。

1. 各参加端末が登録 Merkle Root のメンバーであることを証明する。
2. 同じ端末が同じドローン・同じ時間窓で二度数えられないようにする。
3. 未登録端末・二重提出を否定系テストで拒否する。

### 次: 実観測との完全な束縛

`chainpoc` は RSSI 関係と累積状態を検証する PoC である。実運用には、各ステップを実際の単発 witness 証明、ドローン署名、freshness、端末アテステーションへ接続し、「もっともらしい数値」ではなく「真正な観測」が集約されたことを保証する必要がある。

### 最後: Step D — 最終証明の EVM 着地

集約結果を最終証明に圧縮し、コントラクトで一度だけ検証して `trusted` / `spoof suspected` を記録する。併せてガス量・証明時間・通信量を測定する。

### 実証研究として残ること

- 実機ドローンで距離別 RSSI を収集し、環境ごとの伝搬係数・誤差を較正する。
- 較正データで検知率、誤検知率、必要 witness 数 K を再評価する。
- GPS 偽装、中継攻撃、複数機同時受信、通信断・検閲への限界と対策を評価する。

## 6. 現在の判断

当面の基準構成は、次の役割分担とする。

| 役割 | 当面の方針 |
|---|---|
| スマホの個別観測証明 | Circom / rapidsnark（必要に応じて Noir を比較） |
| 独立検証可能な複数端末の連鎖・集約 | gnark 方式A。重い処理はラズパイ／集約器側も許容 |
| 高速な反復計算の研究候補 | Nova。ただし非信頼端末間のチェーンには追加設計が必要 |
| 最終的な結果の記録 | EVM で最終証明を一度検証 |

この順序なら、性能比較の成果を活かしつつも、入力真正性・Sybil・二重計上という安全性の土台を先に固められる。

## 7. 次の一手

**Step C を Issue として分割し、`aggregator/cmd/chainpoc/` を基準に実装する。**

- C-1: 累積状態と公開出力に membership / nullifier 関連の値を追加
