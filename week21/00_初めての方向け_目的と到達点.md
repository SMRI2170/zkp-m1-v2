# はじめて読む人向け：この研究は何を目指しているか

作成日: 2026-09-28  
元資料: `week21/00_これまでの総まとめ_目的と到達点.md`

---

## まず、一言でいうと

この研究は、**ドローンが発信した「私はここにいます」という位置情報が、本当にありそうな位置かを、周りのスマホで確かめる仕組み**を作るものです。

ただし、確認に協力する人のスマホの位置や、受信した電波の詳しい値は、他人に見せないようにします。

---

## 何が問題なのか

ドローンには **Remote ID（リモートID）** という仕組みがあります。これは、ドローンが自分の識別番号や位置を周囲に電波で知らせる仕組みです。

しかし、その放送を受け取っただけでは、次のような疑問が残ります。

> 「ドローンが伝えた位置は、本当に正しいのだろうか？」

悪意のある人が、遠くにあるドローンの位置を、別の場所にあるように見せる可能性があります。これを **位置詐称（いちさしょう）**、つまり「位置を偽ること」と呼びます。

---

## どうやって確かめるのか

周りにいる複数のスマホを、観測に協力する端末として使います。

各スマホは、次の二つの距離を比べます。

1. **計算した距離**  
   ドローンが放送した位置と、スマホ自身の GPS 位置から計算した距離です。
2. **電波から推定した距離**  
   スマホが受け取った電波の強さから、おおよその距離を推定します。電波は近いほど強く、遠いほど弱くなりやすいためです。

この二つがだいたい合っていれば、「放送された位置はもっともらしい」と考えられます。大きく食い違えば、位置が偽られている疑いがあります。

```text
ドローンが「ここにいる」と電波で知らせる
                 │
                 ▼
周囲のスマホが、自分の位置と受信電波を使って確かめる
                 │
                 ▼
複数のスマホの判定を集める
                 │
                 ▼
「もっともらしい」または「偽装の疑い」を記録する
```

---

## プライバシーはどう守るのか

この確認にはスマホの位置や電波の強さが使われます。しかし、それらをそのまま公開すると、協力者の行動場所や行動履歴が分かってしまうおそれがあります。

そこで **ゼロ知識証明（ZKP）** を使います。

ゼロ知識証明とは、**秘密の値そのものを見せずに、「条件を満たしている」ことだけを証明する技術**です。

この研究では、各スマホは次のような内容だけを証明します。

- 「私が計算した二つの距離は、だいたい合っている」
- または「二つの距離は、大きく食い違っている」

スマホの正確な位置や、生の電波強度の値は公開しません。

---

## なぜスマホを複数使うのか

スマホが1台だけだと、GPS の誤差や電波の乱れ、その端末の故障・不正に影響されやすくなります。

そのため、複数のスマホの結果を集めます。たとえば5台中3台以上が同じ判断なら、その判断を採用する考え方です。

これを **K-of-N（ケー・オブ・エヌ）** と呼びます。

- **N**: 参加した端末の総数
- **K**: 判断を成立させるために必要な最低台数

例: 「5台中3台以上が整合しているなら信頼する」は、K=3、N=5 の K-of-N です。

---

## ここまでにできたこと

研究では、考え方だけでなく、次の部品を実際に作って動かしてきました。

| 作ったもの | できること | この研究での役割 |
|---|---|---|
| スマホアプリ | BLE / Wi-Fi でドローンの Remote ID を受信し、GPS・カメラ・センサー情報を扱う | ドローンの情報を受け取り、観測を始める入口 |
| 電波の判定処理 | 複数回受信した電波強度から代表値を出し、位置からの距離と比べる | 一度だけの電波の乱れに振り回されず、「整合／矛盾」を判断する |
| 個別のゼロ知識証明 | スマホ内で、位置や生の電波強度を出さずに判定結果を証明する | 協力者のプライバシーを守る |
| 複数端末の集計 | 同じドローン・同じ時間帯について、複数のスマホの証明を確認して数える | K-of-N により、1台だけの判断に頼らない |
| ブロックチェーン上の記録 | 証明を検証し、一定数の判定がそろった結果を記録する | 後から結果を確認でき、書き換えにくい記録を残す |
| 証明の連鎖の試作 | 前の集計結果が正しいことを確かめながら、次の端末の判定を追加する | 途中の結果も検証できる形で、順番に集約する |

### もう少し具体的にいうと

最初に、Flutter で作ったスマホアプリに、BLE と Wi-Fi の Remote ID を受信する機能を入れました。スマホは自分の GPS 位置を取得し、受け取った電波の強さも利用できます。

次に、スマホの中で「放送位置から計算した距離」と「電波強度から推定した距離」が合うかを判定し、その判定だけをゼロ知識証明として出せるようにしました。つまり、位置や電波強度の生データをサーバーや他の参加者へ渡さずに済みます。

さらに、複数スマホの証明をブロックチェーン上で検証し、同じドローン・同じ時間帯の結果だけを数える仕組みを実装しました。必要な台数の判定がそろうと、「信頼できそう」または「偽装の疑い」という結果を出せます。

現在はその次の段階として、前の証明を次の証明の中で確認しながら、判定数を順番に増やす「証明の連鎖」も試作済みです。この連鎖により、後から見た人も「途中の結果を飛ばしたり、書き換えたりしていないか」を確認しやすくなります。

---

## 今、どこまで来ているか

現在は、複数の判定を順番にまとめていく仕組みの基本部分まで完成しています。

たとえば、3台のスマホの判定を順に追加し、「整合している端末は2台、疑わしいとした端末は1台」というような合計を、証明つきで引き継げます。

ただし、まだ実運用に必要な大事な部分が残っています。

---

## 次に取り組むこと

次の中心課題は、**同じ人・同じ端末が何度も数えられないようにすること**です。

悪意のある人が自分の端末を何度も参加させると、多数決が不公平になります。このように、1人が多数の偽の参加者を作る攻撃を **Sybil 攻撃（シビル攻撃）** と呼びます。

次の実装では、以下を行います。

- 登録済みの端末だけが参加できるようにする。
- 同じ端末が、同じドローン・同じ時間帯の確認に2回参加できないようにする。
- 登録されていない端末や重複した参加を、仕組みとして受け付けないようにする。

その後、実際の観測データ、ドローンからの署名付き情報、最終結果を記録する仕組みへつなげます。

---

## 大切な限界

この仕組みは、「電波の強さと位置の関係から見て、放送位置が自然か」を確かめるものです。ドローンの本当の位置を100%断定するものではありません。

建物、壁、天候、周囲の電波などで受信電波は変わります。そのため、実際のドローンを使ってデータを集め、環境ごとの誤差を調べる必要があります。

また、電波を中継するような高度な攻撃など、電波の強さだけでは防ぎきれない攻撃もあります。こうした限界を明らかにし、必要な追加対策を考えることも研究の一部です。

week20では、「複数のスマホの判定を、プライバシーを守ったまま、どのように安全に一つへまとめるか」を中心に進めました。主な成果は、設計の整理、証明の連鎖の試作、スマホで動かせるかの実機確認です。

| 証明の連鎖の設計 | 前の証明を次の証明の中で確認してから、次の判定を足す方法を設計した | 途中の集計結果も単独で確認できる形を目指す方針を決めた |

| Step B の実装 | 電波と位置の整合判定を、証明の中で自動計算するようにした | 参加者が「整合している」と勝手に偽って数を増やすことを防げた |
| 不正な入力のテスト | 時間帯の不一致、前の結果の改ざん、矛盾した観測を整合と偽る操作を試した | いずれも証明生成時に拒否されることを確認した |

| 方式の比較 | 連鎖を厳密に確認する方式と、軽く繰り返し計算する方式を比べた | 厳密な方式は重く、軽い方式はスマホで有望だが追加の安全設計が必要と分かった |

### 1. 証明の連鎖を実際に動かした

「証明の連鎖」とは、次の人が新しい判定を追加するときに、前の人までの集計結果が正しいことも一緒に確認する仕組みです。

week20では、3回分の判定を順番につなぐ試作を実装しました。結果は次のように正しく増えました。

```text
1人目：整合 → 整合 1件、疑い 0件
2人目：整合 → 整合 2件、疑い 0件
3人目：矛盾 → 整合 2件、疑い 1件
```

また、各段階の証明はあとから単独でも確認できました。前の証明の時間帯を変えたり、集計数を不自然に書き換えたりすると、次の証明は作れませんでした。

### 2. 「自己申告」をやめ、判定を証明の中で計算した

初期の形では、「この観測は整合している」という結果を参加端末が入力する余地がありました。week20ではこの弱点を改善し、電波から推定した距離と位置から計算した距離の比較を、証明の内部で行うようにしました。

そのため、実際には矛盾している観測を「整合している」として集計数を増やそうとすると、証明の条件を満たせず拒否されます。これは、判定結果だけでなく、**判定の計算過程も正しく行われた**ことを示せるようになった、重要な進展です。

### 3. スマホでどこまで動くかを実機で確認した

計算の重い証明をスマホで実行できるかは、この研究の重要な課題です。Pixel 8 の実機で、次の方式を検証しました。

| 方式 | 実機で確認したこと | この研究での向き・不向き |
|---|---|---|
| Circom | 電波と位置の整合を示す単体証明を生成・確認 | スマホで各端末の観測を証明する用途に向く |
| Noir | 同じ整合判定の証明を生成・確認 | Circom の比較候補として動作を確認 |
| Nova | 3段階の証明の連鎖を生成・確認 | 軽い連鎖計算の候補として有望 |
| gnark | 証明の連鎖を実装・計測 | 厳密に前の証明を確認できる一方、スマホで動かすには重すぎる |

Circom、Noir、Nova は、実機で証明を作って確認するところまで動きました。一方、gnark を使う連鎖の証明は、パソコン上でも1回あたり数秒・大きなメモリを必要としました。そのため当面は、スマホには軽い個別証明を担当させ、重い集約処理は集約器や小型コンピュータ側で担当させる考え方が現実的です。

### 4. 軽い方式（Nova）も試作した

Nova は、前の計算結果を効率よく引き継ぐ方式です。week20では、gnark と同じように「整合 2件、疑い 1件」まで数える試作を作り、Pixel 8 でも1段階あたりおよそ0.5〜1.2秒で動くことを確認しました。

ただし、Nova を別々のスマホの間で安全に受け渡すためには、まだ追加の仕組みが必要です。たとえば、受け取った途中結果を必ず確認してから使うこと、同じ端末を二重に数えないこと、複数人が同時に更新したときの順番を決めることなどです。

そのため、week20の結論は「Nova は性能面で有望だが、すぐに複数端末間の本番用の連鎖へ使うのではなく、安全対策を設計してから使う」というものです。

### week20の到達点

week20で、証明の連鎖そのものと、判定を証明の中で自動計算する部分は動かせました。また、複数の方式を実機で比べ、スマホと集約器の役割分担も具体的になりました。

次に必要なのは、登録済み端末だけを数え、同じ端末の重複参加を防ぐ仕組みです。これが、現在進める Step C につながります。
