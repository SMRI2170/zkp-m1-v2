# Raspberry Pi 4の実機評価計画

作成：2026-10-13。対象：[#44](https://github.com/SMRI2170/zkp-m1-v2/issues/44)。計画段階で、以下の試験は未実施。

## 目的と現在の実機

**Pi4・4GBで、秘密観測を端末内に保持しながら、どの証明方式が正しく・安定して動くかを測る。**
まず動作とメモリ、次に1Hz追従、最後に長時間安定性を評価する。方式の採否は実測後に決める。
単発ZKP、端末内IVC、外部提出用最終ZK証明を分けて記録する。

SSHで確認済み：Raspberry Pi 4 Model B Rev 1.5、Debian 12 bookworm、aarch64。
RAM表示3.7GiB、利用可能3.3GiB、Swap 199MiB・使用0。これは接続時のsnapshotで、性能測定ではない。
CPU温度・電源状態・カーネル・cgroup・空き容量・toolchain・バックグラウンド負荷は開始前に確認する。
接続パスワード、LANアドレス、実キャプチャ、実座標、端末秘密鍵を評価ログへ記録しない。

## 実施順序

| 段階 | 内容 | 完了条件／進める条件 |
|---|---|---|
| 0 環境固定 | OS/kernel/CPU/RAM/温度/電源/Swap/cgroup/storage、各toolchain・commit・lock・patchを記録。専用実験directoryと計測runnerを用意 | メモリ上限・timeout・ログ回収を確認。ビルド失敗と実行失敗を区別できる |
| 1 最小スモーク | **gnark Groth16 → Circom/RapidSnark Groth16 → gnark PLONK → Nova/CycleFold**。各toy回路の正常prove/verifyと改竄拒否 | 各方式に成功ログまたは再現可能なブロッカー。1方式が止まっても他方式を評価する |
| 2 同等RSSI回路 | 既存位置整合性の整数計算を移植。正常・不整合・境界入力と公開結果を照合 | 入力範囲・公開statement・判定の意味を揃える。揃わない方式は別枠にする |
| 3 短い時系列 | Novaは3→10→60→600step。単発方式はN件個別、時間窓一括は実装できた場合の別構成 | 各窓の件数・整合／不整合countと検証結果が期待値に一致。最終ZK有無を明記 |
| 4 1Hz評価 | 独立した単調時計で入力を到着させ、処理時間・待ち行列・欠落・最終化を測る | 60秒→10分。OOM・取りこぼし・処理未完了を記録し、候補を絞る |
| 5 長時間評価 | 有望方式だけ1時間、合格後に24時間の60秒窓反復 | メモリ増加、queue増大、検証失敗、OOM、温度／throttlingを評価 |
| 6 選定 | 正当性・最終ZK・資源・安定性を表にまとめ、候補と不採用理由をADRへ記録 | 本番や端末外への秘密送信を前提にせず、研究用途ごとに結論を出す |

gnark Groth16を最初にする理由は、既存Go回路・依存lock・native verifierの資産があり、
最小のARM64実行と計測runnerの確認に使えるため。最速であると仮定した順序ではない。
RapidSnarkは[公式Linux ARM64手順](https://github.com/iden3/rapidsnark#compile-prover-for-linux-arm64-machine)を固定commitで確認して導入する。
gnarkは[公式概要](https://docs.gnark.consensys.com/overview)とrepoの固定依存を起点にする。

HyperNovaはP1として段階1〜3の後に追加する。旧Novaと新HyperNovaを別workspaceに置き、
HyperNovaはまずtoyのFolding/IVCだけを評価する。終端Decider未実装はN/A。
Noir／Halo2は#45でARM64・4GB条件を絞り込んだ後の追加候補で、P0の完了を待たせない。
Week23で停止した跨Prover binder開発は再開しない。

## 初回セッションの範囲

最初の実行では次の4項目までを目標とする。所要時間の確約はせず、実行結果を優先する。

1. Pi環境inventoryと、cgroup制限下でのrunnerの動作を確認。
2. ホスト側でgnark Groth16の小規模ARM64実行ファイルとlocal-only fixtureを準備。
3. Piで実際にprove→verify。proof／公開入力改竄の拒否も確認。
4. 正常1回の資源ログを確認後、warmup 1回＋20回を測定して最初の結果表を作る。

Piで新たなapt導入やsudo権限が必要かは環境inventory後に判断する。
鍵生成・コンパイルをMacで行う場合、その時間・メモリはPi計測に含めない。
Pi上での鍵読込み・witness生成・prove・verifyは実測する。ビルドだけ成功してもPi prove成功とはしない。

## 回路と入力を揃える

候補資産：`circuits/remoteid_consistency_rel.circom`、`week23/poc/private-pcd/relations.go`、
`nova_poc/uav_chain_step.rs`。相対許容帯の係数は既存の値を固定し、実RF較正の結果とは扱わない。

性能比較の前に、独立した整数reference計算を使い、各回路の判定を検査する。
Circomのbit幅制約とgnark／arkworksのfield比較は同じとは限らないため、
入力の整数範囲・正規化・中間値の範囲・overflow／field wrapを照合する。
必要なrange checkは新しい専用bench回路へ追加し、元の研究PoCは保存する。
係数が同じだけで「同一の暗号的statement」と判定しない。

fixtureは合成値のみ。整合、不整合、帯の上下境界、その直前直後、zero range、範囲外入力を用意する。
**不整合な観測に対する正しい判定証明はverify成功が期待される。**
拒否すべきものは、その判定・count・proof・拘束済み公開入力を偽ったケース。
sessionやpolicyがまだ公開statementにない回路では、その変更拒否を成功項目にしない。

Novaの旧3step baselineは期待state `consistent=2, suspicious=1, steps=3`を確認する。
新規時系列回路でsession/RID/window/policyを追加する場合は、旧baselineとは別revision・鍵にする。
各時系列では`consistent + suspicious = steps`、窓ごとの処理件数、初期/最終stateを照合する。
各方式の公開入力と公開結果が異なる場合、同じ性能列へ混ぜず差を記録する。

## 測定の区間・反復・設定

| 測定層 | 収集する値 |
|---|---|
| 準備 | compile、setup/preprocess、key generation、鍵/SRS容量。実行ホストを明記 |
| cold開始 | プロセス起動、key load、初期化、初回prove。以降のwarmと分離 |
| 観測1件／1step | witness生成、prove/fold、verifyそれぞれの時間、CPU、メモリ |
| 窓の終了 | 最終ZK化/Deciderの時間・RAM、最終verify、proof/public/内部stateのサイズ |
| 1Hz pipeline | arrival→処理開始の待ち、arrival→検証完了の遅延、queue深さ、受信/完了/欠落件数 |
| 全プロセス群 | cgroup memory.current/peak、memory.events、swap、RSS/PSS、温度、CPU周波数、throttling／低電圧 |

初期baselineは同時に1方式、worker 1、実際に制御できるスレッド数1。
次に1/2/4スレッドを比較し、制御できないbackendはN/Aとする。ビルド並列数と実行スレッド数を分ける。
I/O・ログ・検証頻度・page cache条件を固定し、条件変更は別runにする。
短い測定はwarmup 1＋20回。p50/p95/p99は標本数と分位点定義（線形補間）を併記する。
20回のp99だけで長時間の1Hz合格を判断しない。時系列600件以上と長時間結果を併用する。

個別ZKPはN件の全工程、IVCはNstep＋最終化を比較する。
最終化が未実装ならFolding-only欄に記録し、完成ZK証明に対する優位性を結論しない。
proof、public input、wire envelope、内部state、keyのbytesを分離する。

## 1Hzと時間窓の定義

arrivalは`monotonic_start + k * 1秒`に従い、prove完了後のsleepで1Hzを作らない。
60秒窓には60件を入力し、deadline後に残った処理はdrain時間と未処理件数として別計測する。
初期queue上限は60件。overflow時は入力sequenceと件数を記録し、そのrunを「欠落あり」とする。
未処理入力を黙って捨てたり、証明完了時刻を観測時刻へ書き換えない。

60stepごとの再初期化と、1本のIVCを600/3,600step継続する試験は別run。
窓の切替え・最終化・次窓入力が重なる負荷を記録する。
初回は単一workerで実際の待ちを観測し、二重buffer等の変更はその後の改善実験とする。

## 資源制限と停止条件

Piの状態を開始時に再確認し、cgroup v2の**実験プロセス群全体**に暫定的に
MemoryHigh=1200MiB、MemoryMax=1536MiB、MemorySwapMax=0を適用する。
既存のsystem swap設定は勝手に変更せず、実験cgroupの制限とsystem全体のswap使用を区別する。
cgroup機能や権限が不足する場合、重い試験前にrunnerを整備し、不足をブロッカーとして記録する。
これは搭載RAMではなく研究上の証明処理予算であり、未達なら「この予算で未達」とする。

最小スモークのtimeoutは1回180秒、短期benchはrun全体30分を初期値とする。
長期試験は対象の試験時間＋drain猶予を個別設定し、すべての子プロセスへ停止を伝える。
OOM、timeout、verify失敗、状態不一致、低電圧・throttling検出では当該runを停止／判定し、ログを回収する。
温度と電源状態がbaselineと異なる測定は、定常性能の同じ表へ混ぜない。
上限や安全性検査を外して成功扱いにせず、改善後は新しいrun IDで再測定する。

## 暫定的な判断ゲート

| ゲート | 目標 | 未達時の扱い |
|---|---|---|
| G1 正確性 | 正常prove/verifyと、仕様に含まれる改竄拒否が成功 | 性能候補に進めず、原因を修正／記録 |
| G2 資源 | 実験cgroup上限1.5GiB、OOM=0、実験group swap=0 | key load/setup/prove等のどこで超過したかを記録 |
| G3 1Hz | 600件で欠落0、queueが継続増大しない。逐次方式はp99 step<1秒を暫定目標 | バッチ／窓処理としての適合性を別評価。受信1Hzと証明1Hzを混同しない |
| G4 公開用ZK | 秘密Witnessを渡さず最終proofを外部native verifierが検証 | IVC-only研究結果として保存し、外部提出方式には未採用 |
| G5 長期 | 1時間、合格後24時間で検証失敗/OOM/欠落0。RSS/cgroup/queueの増加傾向を分析 | 時間窓reset、threads、buffer等を変更した別条件で再試験 |

数値目標は仮設定。達成してもRF/GPS/RSSIの真値、DRIP trust chain、実UAV同一性、hardware認証を保証しない。
センサー取得やUI、Besu validator、Pixel比較を初回Pi暗号ベンチへ同時投入しない。
Pi生成proofのBesu直接検証は後続ゲートで、承認された鍵利用条件を満たしてから別測定する。
